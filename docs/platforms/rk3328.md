# Rockchip RK3328 (Rock64, NanoPi R2S)

`ARCH=aarch64 BOARD=rk3328`

Almost the whole boot chain is open source, which is what separates this board
from a typical Rockchip part: TF-A's rk3328 platform is upstream, so the only
vendor binary anywhere in the chain is the SPL's DDR training blob from `rkbin`.
It is **not** a zero-blob boot — the boot chain below shows that blob — but it is
the only one, and everything after the SPL is source the build reproduces. For a
chain with no vendor binary at all, see
[Allwinner H616/H618](sun50i-h616.md). Boards are USD 25–35 (Rock64) and USD 27
(NanoPi R2S).

**Build-verified only. Not run on hardware.** That build claim is now
reproduced on every commit by `make check-arm-board-builds`, so the board cannot
silently stop compiling.

## Hardware facts

From upstream Linux at `551c722f40809618230001baccf219193e22fc5a`, files
`arch/arm64/boot/dts/rockchip/rk3328.dtsi` and `rk3328-rock64.dts`:

| Item | Value |
|---|---|
| SoC | Rockchip RK3328, 4× Cortex-A53 |
| GIC | `interrupt-controller@ff811000`, `"arm,gic-400"` — **GICv2** |
| UART0 | `serial@ff110000`, 0x100 bytes, `GIC_SPI 55` → **IRQ 87**, `"rockchip,rk3328-uart", "snps,dw-apb-uart"` |
| Ethernet | `ethernet@ff540000` (`gmac2io`), 0x10000, `GIC_SPI 24` → IRQ 56, `"rockchip,rk3328-gmac"` |
| eMMC | `mmc@ff520000`, 0x4000, `GIC_SPI 14` → IRQ 46, `"rockchip,rk3328-dw-mshc"` |
| Clock controller | `clock-controller@ff440000` |
| Register file | `syscon@ff100000` |
| Timer | DZI 24 MHz |

Two of these are worth calling out because they are why this board is cheap to
port. `"snps,dw-apb-uart"` is a 16550, which every architecture's `console.h`
already declares. `"arm,gic-400"` is GICv2, which is exactly what
`kernel/arch/aarch64/include/platform.h`'s `GICD_BASE`/`GICC_BASE` pair drives —
no GICv3 work.

**The GMAC is a Synopsys DWMAC** (`rockchip,rk3328-gmac`, upstream `dwmac-rk.c`),
the same IP family as `kernel/drivers/net/ls2k_gmac.c`. That is a near-reuse
rather than a new driver, and it is the main reason this board is worth doing.

Rock64 aliases `ethernet0` to `gmac2io`; the NanoPi R2S aliases it to `gmac1`,
which is a different base. `rk3328_platform.h` follows Rock64.

## Boot chain

```text
Rockchip boot ROM  →  SPL (rkbin DDR blob)  →  TF-A BL31 (open source)  →  U-Boot  →  kernel
```

mainline U-Boot has `rock64-rk3328_defconfig`, and TF-A exposes PSCI, which is
what the aarch64 port already uses.

## Scope of this port

Brings up: RAM, the console UART, the GICv2, PSCI `poweroff`/`reboot`.

Deliberately absent, each needing real work:

- **eMMC.** `rockchip,rk3328-dw-mshc` is a DesignWare MSHC, upstream driven by
  `dwmci-mshc`. A20OS's `dw_sdio.c` targets the older DesignWare SDIO/MMC
  layout that the VisionFive 2's dw-mci uses. Close relatives, not the same
  registers.
- **Ethernet.** DWMAC, so `ls2k_gmac.c` is the starting point — but it needs a
  Rockchip CRU/GRF clock-and-resort sequence first, and that has not been
  derived.
- **SMP.** `.smp` is `NULL`. Which CPUs exist is a bootloader and DT question
  that has not been checked on hardware, and `porting-guide.md` is explicit that
  a board which cannot start secondaries must leave it NULL rather than supply a
  fake ops table.

`early_init()` deliberately does **not** touch the CRU. U-Boot enabled the
console UART's clocks before handing over, so the serial port works without it.
Every other peripheral on this SoC does need CRU gate and reset writes.

## Deploying

`tools/a20` is the deployment tool. There is no make command here, and that is
deliberate: this board has no block driver, so there is no card to write and
nothing for `dd` to put an image on. The artifact is the kernel plus the
commands that hand it to the boot chain already on the board.

### What you get

```sh
tools/a20 package rk3328
```

writes `build/rk3328/handoff/`: `kernel.bin`, `uboot.cmd` with the exact lines
to run at the U-Boot prompt, and a `README.md` carrying the same instructions.

The load address is **not** written in this document or in the instance. `a20
package` reads it out of the first `PT_LOAD` header of the kernel it just built,
so a board whose linker script relocates the image cannot end up with a stale
address here.

No device tree is shipped, on purpose: U-Boot passes its own board DTB in `a1`,
and the kernel is built to be told the layout rather than to read it.

### Getting it onto the board

1. Boot the board's own way, so its firmware and U-Boot are running. Keep the
   bootloader on the medium — it is the only way back.
2. Interrupt U-Boot's autoboot.
3. Tell U-Boot where the host is, then load the kernel:

   ```text
   setenv serverip <your-host-ip>
   setenv ipaddr <board-ip>
   tftp <loadaddr> kernel.bin
   ```

   Load `kernel.bin` from `build/rk3328/handoff/`. Substitute the address
   `uboot.cmd` prints for `<loadaddr>`.
4. Start the kernel:

   ```text
   booti <loadaddr> - <loadaddr>
   ```

   The `-` is the device tree pointer, left empty because U-Boot passes its own
   board DTB in `a1` itself.

### Verifying

```sh
tools/a20 deploy rk3328     # build, package, print the commands, then check
tools/a20 console rk3328    # just watch and check an already-running board
```

The console is `/dev/ttyUSB0` at 1500000. Override the node if your adapter
enumerates differently — `ls /dev/ttyUSB*` before plugging in and after.

**On this architecture the only boot evidence is `System ready`.** There is no
`[FDT]` line: only riscv64 and loongarch parse a device tree, and the aarch64
port has no DT-based RAM narrowing, so `console_check` waits for that one string
and nothing else. `System ready` is printed by `kernel/main.c` and means the
kernel reached userspace.

### The load address is the first thing to check

`KERNEL_ENTRY` and `PHYS_BASE` are compile-time constants. U-Boot honours a load
address from its own environment or bootflow, and that need not be where A20OS
linked the image. A kernel loaded somewhere other than its link address jumps to
an address it was not built for and produces nothing at all -- no banner, no
panic, just silence.

### If it does not boot

Ordered by what actually fails first.

1. **Nothing on the console.** Wrong UART or pinmux. RK3328 firmware releases
   the UART clock, so silence usually means the firmware did not run, not that
   the kernel is wrong.
2. **U-Boot banner, then silence.** The load address, above. This is the most
   likely failure on this board.
3. **`System ready` never appears but earlier boot output does.** The kernel
   reached userspace preparation and stopped. That is past bring-up; see
   `porting-guide.md`.

## Unverified: DRAM_BASE

The Rock64 device tree declares **no memory node** — the bootloader passes the
layout — so `PHYS_MEMORY_BASE = 0x0` in `rk3328_platform.h` is the RK3328 DDRC
aperture from the SoC memory map, not a value read off a board. `KERNEL_ENTRY`
likewise. Confirm both against your own U-Boot (`bdinfo`) before trusting a boot
past the console.

Note that this differs from the aarch64 QEMU default of `0x40000000`, which is
why the board needed a `platform.h` override block rather than compiling
unchanged.

## Before claiming hardware verification

1. Build, then compare `bdinfo` in U-Boot against `PHYS_MEMORY_BASE` /
   `KERNEL_ENTRY` and correct both together if they differ.
2. Boot and confirm the console banner on UART0. The RK3328's own UART runs at
   1.5 Mbaud, not 115200 — `instances/rk3328.toml` sets that, and it is a common
   first-hour mistake.
3. Record the acceptance table from `porting-guide.md`.
