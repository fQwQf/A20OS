# Rockchip RK3328 (Rock64, NanoPi R2S)

`ARCH=aarch64 BOARD=rk3328`

The zero-blob-boot ARM option in the tree: TF-A's rk3328 platform is open
source, so the only vendor binary in the chain is the SPL's DDR training blob
from `rkbin`. Boards are USD 25–35 (Rock64) and USD 27 (NanoPi R2S).

**Build-verified only. Not run on hardware.**

## Hardware facts

From upstream Linux at `551c722f40809618230001baccf219193e22fc5a`, files
`arch/arm64/boot/dts/rockchip/rk3328.dtsi` and `rk3328-rock64.dts`:

| Item | Value |
|---|---|
| SoC | Rockchip RK3328, 4× Cortex-A53 |
| GIC | `interrupt-controller@ff811000`, `"arm,gic-400"` — **GICv2** |
| UART0 | `serial@ff110000`, 0x100 bytes, `GIC_SPI 55` → **IRQ 87**, `"rockchip,rk3328-uart", "snps,dw-apb-uart"` |
| Ethernet | `ethernet@ff540000` (`gmac2io`), 0x10000, `GIC_SPI 24` → IRQ 56, `"rockchip,rk3328-gmac"` |
| eMMC | `mmc@ff520000`, 0x4000, `GIC_SPI 14` → IRQ 46, `"rockchip,rk3328-dw-mshc"` |
| Clock controller | `clock-controller@ff440000` |
| Register file | `syscon@ff100000` |
| Timer | DZI 24 MHz |

Two of these are worth calling out because they are why this board is cheap to
port. `"snps,dw-apb-uart"` is a 16550, which every architecture's `console.h`
already declares. `"arm,gic-400"` is GICv2, which is exactly what
`kernel/arch/aarch64/include/platform.h`'s `GICD_BASE`/`GICC_BASE` pair drives —
no GICv3 work.

**The GMAC is a Synopsys DWMAC** (`rockchip,rk3328-gmac`, upstream `dwmac-rk.c`),
the same IP family as `kernel/drivers/net/ls2k_gmac.c`. That is a near-reuse
rather than a new driver, and it is the main reason this board is worth doing.

Rock64 aliases `ethernet0` to `gmac2io`; the NanoPi R2S aliases it to `gmac1`,
which is a different base. `rk3328_platform.h` follows Rock64.

## Boot chain

```text
Rockchip boot ROM  →  SPL (rkbin DDR blob)  →  TF-A BL31 (open source)  →  U-Boot  →  kernel
```

mainline U-Boot has `rock64-rk3328_defconfig`, and TF-A exposes PSCI, which is
what the aarch64 port already uses.

## Scope of this port

Brings up: RAM, the console UART, the GICv2, PSCI `poweroff`/`reboot`.

Deliberately absent, each needing real work:

- **eMMC.** `rockchip,rk3328-dw-mshc` is a DesignWare MSHC, upstream driven by
  `dwmci-mshc`. A20OS's `dw_sdio.c` targets the older DesignWare SDIO/MMC
  layout that the VisionFive 2's dw-mci uses. Close relatives, not the same
  registers.
- **Ethernet.** DWMAC, so `ls2k_gmac.c` is the starting point — but it needs a
  Rockchip CRU/GRF clock-and-resort sequence first, and that has not been
  derived.
- **SMP.** `.smp` is `NULL`. Which CPUs exist is a bootloader and DT question
  that has not been checked on hardware, and `porting-guide.md` is explicit that
  a board which cannot start secondaries must leave it NULL rather than supply a
  fake ops table.

`early_init()` deliberately does **not** touch the CRU. U-Boot enabled the
console UART's clocks before handing over, so the serial port works without it.
Every other peripheral on this SoC does need CRU gate and reset writes.

## Building

```sh
make ARCH=aarch64 BOARD=rk3328 ABI=linux BRINGUP=1 kernel-only
```

## Unverified: DRAM_BASE

The Rock64 device tree declares **no memory node** — the bootloader passes the
layout — so `PHYS_MEMORY_BASE = 0x0` in `rk3328_platform.h` is the RK3328 DDRC
aperture from the SoC memory map, not a value read off a board. `KERNEL_ENTRY`
likewise. Confirm both against your own U-Boot (`bdinfo`) before trusting a boot
past the console.

Note that this differs from the aarch64 QEMU default of `0x40000000`, which is
why the board needed a `platform.h` override block rather than compiling
unchanged.

## Before claiming hardware verification

1. Build, then compare `bdinfo` in U-Boot against `PHYS_MEMORY_BASE` /
   `KERNEL_ENTRY` and correct both together if they differ.
2. Boot and confirm the console banner on UART0. The RK3328's own UART runs at
   1.5 Mbaud, not 115200 — `instances/rk3328.toml` sets that, and it is a common
   first-hour mistake.
3. Record the acceptance table from `porting-guide.md`.
