# Rockchip RK3328（Rock64、NanoPi R2S）

> **1.0 范围（2026-10-22）**：本板移出 1.0 运行矩阵。没有板卡，SD/eMMC 与 GMAC 驱动无法在实体板上验证；源码、构建目标与本文档保留，不再作为 1.0 启动/存储/网络能力的验收对象。硬件到位后可重新立项。

`ARCH=aarch64 BOARD=rk3328`

这条启动链几乎全部开源，这正是它区别于典型 Rockchip 芯片的地方：TF-A 的 rk3328 平台在上游，因此链中
唯一的厂商二进制是来自 `rkbin` 的 SPL DDR 训练 blob。它**不是**零 blob 启动——下面的启动链画出了那个
blob——但它是唯一的一个，SPL 之后的一切都是构建可复现的源码。想要完全没有厂商二进制的链，见
[Allwinner H616/H618](sun50i-h616.md)。板价约 25–35 美元（Rock64）与 27 美元（NanoPi R2S）。

**只验证到构建。未在硬件上运行。** 该构建结论现在由 `make check-arm-board-builds` 在每次提交上复现，
因此这块板不会悄悄编译不过。

## 硬件事实

来自上游 Linux `551c722f40809618230001baccf219193e22fc5a` 的
`arch/arm64/boot/dts/rockchip/rk3328.dtsi` 与 `rk3328-rock64.dts`：

| 项 | 取值 |
|---|---|
| SoC | Rockchip RK3328，4× Cortex-A53 |
| GIC | `interrupt-controller@ff811000`，`"arm,gic-400"`——**GICv2** |
| UART0 | `serial@ff110000`，0x100 字节，`GIC_SPI 55` → **IRQ 87**，`"rockchip,rk3328-uart", "snps,dw-apb-uart"` |
| 以太网 | `ethernet@ff540000`（`gmac2io`），0x10000，`GIC_SPI 24` → IRQ 56，`"rockchip,rk3328-gmac"` |
| eMMC | `mmc@ff520000`，0x4000，`GIC_SPI 14` → IRQ 46，`"rockchip,rk3328-dw-mshc"` |
| 时钟控制器 | `clock-controller@ff440000` |
| Register file | `syscon@ff100000` |
| 定时器 | DZI 24 MHz |

其中两项值得点名，因为它们正是这块板移植便宜的原因。`"snps,dw-apb-uart"` 是 16550，各架构的 `console.h`
都已经声明。`"arm,gic-400"` 是 GICv2，正是 `kernel/arch/aarch64/include/platform.h` 的 `GICD_BASE`/
`GICC_BASE` 那一对已经驱动的对象——不需要做 GICv3。

**GMAC 是 Synopsys DWMAC**（`rockchip,rk3328-gmac`，上游 `dwmac-rk.c`），与
`kernel/drivers/net/ls2k_gmac.c` 同属一个 IP 家族。这接近复用而非新驱动，也是这块板值得做的
主要原因。

Rock64 把 `ethernet0` 别名到 `gmac2io`；NanoPi R2S 别名到 `gmac1`，基址不同。`rk3328_platform.h` 按
Rock64 走。

## 启动链

```text
Rockchip boot ROM  →  SPL（rkbin DDR blob）  →  TF-A BL31（开源）  →  U-Boot  →  kernel
```

mainline U-Boot 有 `rock64-rk3328_defconfig`，TF-A 暴露 PSCI，正是 aarch64 移植已经在用的东西。

## 本移植的范围

完成：RAM、控制台 UART、GICv2、PSCI `poweroff`/`reboot`。

刻意缺席，每一项都需要真正的工作：

- **eMMC。** `rockchip,rk3328-dw-mshc` 是 DesignWare MSHC，上游由 `dwmci-mshc` 驱动。A20OS 的
  `dw_sdio.c` 面向 VisionFive 2 的 dw-mci 所用的较老 DesignWare SDIO/MMC 布局。是近亲，但不是同一组
  寄存器。
- **以太网。** DWMAC，所以 `ls2k_gmac.c` 是起点——但它需要先有一套 Rockchip CRU/GRF 的时钟与复位序列，
  而该序列还没有推出来。
- **SMP。** `.smp` 为 `NULL`。存在哪些 CPU 是 bootloader 与 DT 的问题，尚未在硬件上核对；
  `porting-guide.md` 明确规定：无法启动从核的板子应保持 NULL，而不是提供一个假的 ops 表。

`early_init()` 刻意**不**碰 CRU。U-Boot 在交接之前已经使能控制台 UART 的时钟，所以串口不需要它。
这颗 SoC 上其他每个外设都需要 CRU 的 gate 与 reset 写入。

## 部署

部署工具是 `tools/a20`。这里没有 make 命令，这是刻意的：本板没有块驱动，所以没有卡可写，也没有东西让
`dd` 去写镜像。产物是内核，加上把内核交给板上已有启动链的那几条命令。

### 你会得到什么

```sh
tools/a20 package rk3328
```

写出 `build/rk3328/handoff/`：`kernel.bin`、在 U-Boot 提示符下逐行执行的 `uboot.cmd`，以及携带同样说明
的 `README.md`。

装载地址**不**写在本文件或实例里。`a20 package` 从刚构建出的内核的第一个 `PT_LOAD` 头里读出它，因此链接
脚本会重定位镜像的板子不会在这里留下过期地址。

刻意不提供 device tree：U-Boot 在 `a1` 里传入它自己的板级 DTB，而内核是按"被告知布局"而不是"自己读取
布局"来构建的。

### 把它弄到板上

1. 按板子自己的方式启动，让它的固件与 U-Boot 跑起来。把 bootloader 留在介质上——它是唯一的退路。
2. 打断 U-Boot 的自动启动。
3. 告诉 U-Boot 主机在哪，然后装载内核：

   ```text
   setenv serverip <你的主机 IP>
   setenv ipaddr <板子 IP>
   tftp <loadaddr> kernel.bin
   ```

   从 `build/rk3328/handoff/` 取 `kernel.bin`，把 `<loadaddr>` 换成 `uboot.cmd` 打印出的地址。
4. 启动内核：

   ```text
   booti <loadaddr> - <loadaddr>
   ```

   中间的 `-` 是 device tree 指针，留空是因为 U-Boot 自己会在 `a1` 里传入它自己的板级 DTB。

### 验证

```sh
tools/a20 deploy rk3328     # 构建、打包、打印命令，然后检查
tools/a20 console rk3328    # 只观察并检查一块已在运行的板子
```

控制台是 `/dev/ttyUSB0`，1500000 波特。若适配器枚举成别的节点，改掉它——插拔前后各执行一次
`ls /dev/ttyUSB*`。

**在这个架构上，唯一的启动证据是 `System ready`。** 没有 `[FDT]` 行：只有 riscv64 与 loongarch 解析
device tree，aarch64 移植没有基于 DT 的 RAM 收窄，因此 `console_check` 只等这一个字符串。`System ready`
由 `kernel/main.c` 打印，意味着内核进入了用户态。

### 装载地址是第一个要查的东西

`KERNEL_ENTRY` 与 `PHYS_BASE` 是编译期常量。U-Boot 遵循它自己环境或 bootflow 里的装载地址，而那不一定
是 A20OS 链接镜像的地址。内核被装到链接地址之外，就会跳到一个它并非为此构建的地址，结果是完全没有输出
——没有 banner、没有 panic，只有静默。

### 如果启动不了

按实际最先出问题的顺序排列。

1. **控制台什么都没有。** UART 或 pinmux 错了。RK3328 固件释放 UART 时钟，所以静默通常意味着固件没跑，
   而不是内核错了。
2. **U-Boot banner 之后静默。** 装载地址，见上。这是本板最可能的失败点。
3. **`System ready` 始终不出现，但前面有启动输出。** 内核走到了用户态准备阶段就停了。那已过 bring-up，
   见 `porting-guide.md`。

## 未验证：DRAM_BASE

Rock64 的 device tree **没有 memory 节点**——布局由 bootloader 传入——因此 `rk3328_platform.h` 里的
`PHYS_MEMORY_BASE = 0x0` 取自 SoC 内存映射中的 RK3328 DDRC 孔径，而不是从板上读出的值。`KERNEL_ENTRY`
同理。在信任越过控制台之后的启动之前，先拿你自己的 U-Boot（`bdinfo`）核对两者。

注意这与 aarch64 QEMU 默认的 `0x40000000` 不同，也正是这块板需要一段 `platform.h` 覆盖而不是原样编译的
原因。

## 在宣称硬件验证之前

1. 构建，然后把 U-Boot 里的 `bdinfo` 与 `PHYS_MEMORY_BASE` / `KERNEL_ENTRY` 对比，若不同就一起改正。
2. 启动并在 UART0 上确认控制台 banner。RK3328 自己的 UART 跑 1.5 Mbaud，不是 115200——`instances/rk3328.toml`
   设的正是它，这也是常见的入门级错误。
3. 按 `porting-guide.md` 记录验收表。
