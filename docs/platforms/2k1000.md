# LS2K1000-DP-V10 Hardware Facts

This file records parameters verified on the target board.  Porting code must prefer the vendor DTB, the running vendor Linux, and matching vendor-driver behavior over conflicting addresses in the processor manual.

## Target and Recovery Baseline

- Board: LS2K1000-DP-V10
- CPU: Loongson-2K1001 / LA264
- RAM fitted: 1 GiB
- Firmware: U-Boot 2022.04-v2.1.0-00583-g2ed41674
- Serial console: NS16550A at physical `0x1fe20000`, 115200 8N1
- WSL serial device observed during the latest 2026-08-18 run: `/dev/ttyUSB0`. The number changed from an earlier `/dev/ttyUSB1` enumeration and must be rechecked after USB/IP reattachment.
- A20OS RAM load address: cached DMW address `0x9000000002000000`
- A physical reset must continue to boot the unchanged vendor Linux image.

Do not run `saveenv`, `sf write`, or `sf erase`, and do not overwrite `/boot/uImage`.  Experimental A20OS images are loaded from new `/boot` names and executed from RAM only.

## Verified Memory Window

- Cached RAM DMW: `0x9000000000000000 + physical`
- Uncached MMIO DMW: `0x8000000000000000 + physical`
- A20OS allocator window: physical `0x00200000..0x0b000000`
- Kernel load/entry physical address: `0x02000000`
- Firmware-owned memory begins below the full 1 GiB limit; the restricted allocator window must remain in place until the complete reserved-memory map is understood.

```text
UART0 route byte       0x23

bank-0 polarity       0x00000000

```

The live route byte proves that bit `0x20` selects HWI1 and low bits `0x3` select both cores.  Since A20OS currently supports only CPU0, its UART0 route value is `0x21`.  The earlier `0x81` estimate was not hardware-verified and must not be used.

Addresses `0x1fe11400` and `0x1fe11040` from the processor manual conflict with this board's DTB and running kernel.  They are not used by the port.

## GMAC and PHY Facts

Read-only inspection of the running vendor Linux on 2026-08-18 established:

| Item | GMAC0 | GMAC1 |
| --- | --- | --- |
| Physical register window | `0x40040000..0x40047fff` | `0x40050000..0x40057fff` |
| Compatible | `snps,dwmac-3.70a`, `ls,ls-gmac` | same |
| LIOINTC sources | `12`, `13` | `14`, `15` |
| Interface mode | RGMII | RGMII |
| PHY address | `0` | `0` |

Both controllers identify as DWMAC1000 with user ID `0xd1` and Synopsys ID `0x37`.  Linux reports support for normal and enhanced/alternate descriptors and uses ring mode.  GMAC0's PHY ID read by A20OS is `0x0000010a`; vendor Linux binds the matching Motorcomm YT85xx driver.  With no Ethernet cable, vendor Linux keeps both interfaces administratively up but reports `NO-CARRIER`, unknown speed/duplex, and `Link detected: no`.  A20OS must treat this as a successfully discovered interface with carrier down, not as a probe failure.

The current Phase 3 implementation uses the controller's basic 16-byte ring descriptor mode, polls PHY BMSR twice to account for its latched-low link bit, and leaves both DMA interrupts and the GMAC LIOINTC sources disabled.  It also performs cache maintenance before reading DMA ownership and before returning ownership.  These changes are implemented and build/QEMU-regression-validated. The no-cable probe and link-down integration are physical-board-validated; descriptor data transfer is not.

## AHCI and SATA Facts

Read-only inspection of the vendor DTB, Linux, and U-Boot established:

| Item | Value | Evidence |
| --- | --- | --- |
| AHCI register window | physical `0x400e0000..0x400effff` | vendor DTB/Linux |
| LIOINTC source | `19` | vendor DTB and `/proc/interrupts` |
| Controller version | AHCI `1.3` | U-Boot `scsi reset` |
| Implemented ports | one SATA port | U-Boot controller report |
| Disk capacity | `62,533,296` 512-byte sectors | U-Boot and vendor Linux |
| Linux partition | MBR type `0x83`, start `4,194,367`, length `58,338,929` | vendor Linux |
| Root filesystem | ext4, 4096-byte blocks | vendor Linux |

The A20OS platform front end now supplies this MMIO window directly to the shared AHCI core. It does not use PCI enumeration or QEMU's ECAM window. The experimental path is polling-only: source 19 and controller interrupts remain masked. AHCI command-list, receive-FIS, command-table, and transfer buffers use the alignments required by the AHCI specification, and the shared driver keeps host and per-port register bases separate.

`STORAGE_READ_ONLY=1` is a separate build profile. Its write fence is enforced at the AHCI command layer and again by the MBR partition wrapper and VFS read-only mount. It recognizes a valid DOS/MBR `0x83` primary partition and mounts a clean ext4 filesystem at `/extra`. If ext4 has the incompatible `needs_recovery` feature set, A20OS refuses the mount and continues to the RAM shell; it does not replay the journal. No A20OS write path is enabled for the board disk.

The implementation is QEMU-validated with an `ich9-ahci` test disk: IDENTIFY, MBR parsing, clean ext4 read-only mounting, write-open rejection with `EROFS`, full-file streaming reads, and samples immediately below and above 4 GiB all passed. A deliberately dirty ext4 image was refused, and test-disk SHA-256 was unchanged before and after both runs. The same polling path is also physical-board-validated: the board reported `SSTS=0x123`, `TFD=0x50`, `62,533,296` sectors, selected the MBR `0x83` partition, and mounted ext4 read-only at `/extra`.

## Current Validation State

- A RAM-only shell, four-level user page tables, TLB refill, process syscalls, timer interrupts, timeout wakeup, idle wakeup, and single-core preemption have been physical-board-validated.
- The cooperative build remains the polling-console fallback.
- LIOINTC support starts with only UART0 source 0.  Other sources remain masked until each device path receives a focused board test.
- The LS2K1000 AHCI platform/polling path, MBR partition wrapper, ext4 read-only mount, and large-file reader are QEMU- and physical-board-validated. AHCI source 19 stays masked and storage writes remain unsupported.
- PCI configuration, GMAC data transfer, and SMP remain unvalidated.
- The Phase 3 GMAC candidate accepts carrier-down as a non-fatal state and exposes it to lwIP; this no-cable path is physical-board-validated. Link-up, descriptor data transfer, ping, and socket traffic still require a cable.
