# 龙芯 2K0300 久久派

当前提供单核内核初始化配置和 U-Boot RAM ELF 装载。实机运行状态：未验证。
目标是先在原厂固件之后启动内核，核验 UART、计时器、内存和异常入口。当前实例设置
`BRINGUP=1`，没有用户空间，也不把编译成功视为板卡适配完成。


## 串口交互 shell 配置

`ls2k0300-shell` 实例嵌入静态链接的 `/bin/init`、`mksh` 和基本命令。
它采用完整用户态启动路径（`bringup=false`、`ramfs_user=true`），不需要根磁盘。
默认嵌入 17 个程序：`init mksh help ls cat ps sleep timer_preempt timer_idle`
和 `echo uname mkdir rm cp sync poweroff reboot`。启动时保留 RAMFS 的 `/bin`，
不会把含内核与 DTB 的启动 FAT 分区自动覆盖挂载到这里。
原 `ls2k0300` 实例仍用于内核初始化验收，二者不能互换验收标准。

```sh
tools/a20 build ls2k0300-shell
tools/a20 package ls2k0300-shell
tools/a20 console ls2k0300-shell
```

交接包仍为 `build/ls2k0300/handoff`；按本文的 DDR/LMB 检查及
`deploy --auto-handoff --transfer usb|mmc|tftp` 流程加载 ELF。
打包会重新生成所选实例对应的内核与 handoff，公共 handoff 目录不得混用旧包。

串口接线、电平、波特率和固件要求沿用本文。`System ready` 只表示内核就绪；
验收还须看到 init 启动 mksh，实际输入并检查输出：

```sh
echo A20_SERIAL_OK
uname -a
ls /bin
cat /proc/meminfo
mkdir /tmp/check
echo hello > /tmp/check/message
cat /tmp/check/message
rm /tmp/check/message
sync
poweroff
```

文件系统为 RAM-only，重启后丢失写入。最小用户构建仅编译嵌入命令，不构建
fastfetch、FFmpeg 或完整发行版。这个配置不包含 SSH 服务，也不承诺网卡、
显示或音频可用。当前状态为交叉构建与封装检查；板上执行仍须实机验收。

## 资料与地址依据

| 项目 | 已查证的依据 | 此阶段采用方式 |
| --- | --- | --- |
| CPU | 龙芯产品页：一个 64 位 LA264 核；数据手册列出双精度 FPU | 单核；标量 FP 保存/恢复；不假定支持 LSX |
| UART0 | 用户手册 v1.01 第 3.2/11 章、Linux DTS 补丁：`0x16100000` | 16550 字节寄存器，保留固件波特率、时钟和复用设置 |
| 中断控制器 | 手册第 3.5 章及 Linux DTS：主块 `0x16001400`，CPU0 ISR `0x16001040` | 两组 32 路 LIOINTC；映射至 HWI0/HWI2，支持高/低电平、上升/下降沿；实机投递待验收 |
| 时钟 | SoC 的参考晶振为 120 MHz；核内稳定计数器参数由 CPUCFG.4/5 描述 | 按 `base × multiplier / divisor` 运行时读取，避免沿用 QEMU 100 MHz |
| 内存 | 参考 DTS 的低内存银行从 `0x00200000` 到 `0x0f000000` | 只配置 `[2 MiB, 128 MiB)`；交付板固件必须确认这段可用 |
| 固件 | 板厂存在 PMON 和新世界 U-Boot；厂商 `99pi_wifi` 配置为 U-Boot 2022.04 分支 | 保留现有固件；先读版本和内存布局，分支处理启动方式 |

**2K0300 的外设地址不等于 2K1000LA。** 没有复用 2K1000 的 UART、LIOINTC、GMAC、
AHCI、PCI 窗口或硬编码 DTB 地址。高内存不纳入初始分配器；实际容量和板卡版本须按实际板卡确认。

## SD / eMMC 支持边界

A20OS 当前没有 2K0300 SDIO/eMMC 块驱动。SDIO0/1 位于 `0x16140000` /
`0x16148000`，其寄存器协议与 DesignWare、sunxi MMC 均不同，不能复用这些驱动的
compatible 绑定。官方手册 v1.01 第 15.4.1 节步骤 6、15.4.2 节步骤 6 明确要求数据
传输配置 DMA；表 15-34/35 将 `SDI_DAT`（`+0x40`）列为只读、用于 DMA 操作。
`DMA_en` 控制位和 FIFO 状态寄存器本身不足以证明支持 CPU PIO 读写。

后续驱动需要实现控制器专用 DMA：读/写入口分别为控制器基址 `+0x800` / `+0x400`，
描述符和 64 位地址格式见手册第 16.4 节，并需确认交付板卡槽连接、pinmux、输入时钟、
SDIO/eMMC 模式及 DMA 一致性配置。现有 U-Boot 读取 SD/USB 文件的能力属于固件。
[Linux v6.17 的 Loongson MMC 驱动](https://github.com/torvalds/linux/blob/v6.17/drivers/mmc/host/loongson2-mmc.c)
也对所有数据请求启用 DMA；该版本匹配表只有 2K0500/1000/2000，未声明 2K0300，
其控制器勘误不能未经确认直接套用。

## 构建主机依赖

使用 Linux、GNU make、Python 3.11+、`loongarch64-linux-gnu-gcc` 与同前缀 binutils。Debian 13 可安装以下包；其他发行版若没有交叉包，需安装提供该前缀的 LoongArch GNU 工具链并将其 `bin` 放入 PATH，不能用宿主 x86 GCC 替代：

```sh
sudo apt-get install build-essential git curl ca-certificates python3 \
  gcc-loongarch64-linux-gnu binutils-loongarch64-linux-gnu libc6-dev-loong64-cross
command -v loongarch64-linux-gnu-gcc
command -v loongarch64-linux-gnu-objcopy
```

安装 rustup 后配置仓库指定的 Rust 1.96.0；若尚无 rustup，可先执行下面前两条命令。已有 rustup 时可跳过安装器：

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/a20-rustup-init.sh
sh /tmp/a20-rustup-init.sh -y --profile minimal --default-toolchain 1.96.0
. "$HOME/.cargo/env"
rustup toolchain install 1.96.0 --profile minimal
rustup target add --toolchain 1.96.0 loongarch64-unknown-none
```

下列仓库命令均在 A20OS 源码根目录执行；首次构建先运行 `git submodule update --init --recursive`。主机 Python 必须为 3.11 或更新版本，可用 `python3 --version` 确认。首次下载源码、Rust 组件和 Cargo 依赖需要联网。

## 部署

下面的自动交接仅针对**原厂 U-Boot**。工具会识别 `PMON>` 并单独报告，不会把
U-Boot 命令发给 PMON。全程保留原厂 SPI 固件、启动菜单和存储分区，只把 ELF 临时加载到 RAM。
A20OS 的 SD/USB 驱动尚未适配，不影响使用 U-Boot 已有的驱动完成这次加载。

1. 按板上调试串口标识连接 TX/RX/GND，使用 3.3 V TTL 适配器；板上 TX 接适配器 RX，
   板上 RX 接适配器 TX，GND 相连。若板卡已有 USB 串口桥，直接插入后执行
   `ls -l /dev/serial/by-id/` 找到新增设备；不要凭 USB 的插入顺序固定 `/dev/ttyUSB0`。
   电源仍使用板厂指定接口；不通过未知的串口 VCC 引脚供电。
2. 在 `instances/ls2k0300.toml` 中将 `target.serial` 占位符改为实际稳定串口路径。
   完成上面的主机准备后，在仓库根目录执行：

   ```sh
   tools/a20 check instances/ls2k0300.toml
   tools/a20 package ls2k0300
   ```

3. 选下述 USB、SD 或网络方式之一准备 ELF。先启动捕获，再给板上电；如果板已自动进入 Linux，
   在工具等待期间重启板卡或断电重上。工具在等待提示符时每 0.5 秒发送 `c`，这是厂商
   `CONFIG_AUTOBOOT_STOP_STR="c"` 指定的停止键；启动菜单的键是 `m`，不是 `c`。

### USB：无需配置网络

将正常格式化的 FAT U 盘插在开发机，执行 `lsblk -o NAME,FSTYPE,MOUNTPOINTS`
确定目标卷的实际挂载根目录，然后一次完成构建、校验和文件放置：

```sh
tools/a20 deploy ls2k0300 --stage-mount /media/USER/YOUR_USB_VOLUME --no-console
```

该命令只在明确选择的、实际已挂载且可写的 FAT 卷创建 `/a20/kernel.elf`；
不会要求 UF2 板卡身份，也不写整盘。它拒绝 symlink 和不同 hash 的已有文件；
相同文件允许幂等重跑，复制完成后对文件与目录执行 fsync。
若存在旧版 ELF，先自行保存或移走旧文件再重跑，工具不会直接覆盖它。
也可使用独立入口，仅预览时加 `--dry-run`：

```sh
python3 tools/ls2k0300_handoff.py stage --mount /media/USER/YOUR_USB_VOLUME
```

正常卸载卷后拔下 U 盘，插入板卡的 USB **Host** 口，再启动 RAM 交接：

```sh
tools/a20 deploy ls2k0300 --auto-handoff --transfer usb
```

默认使用 U-Boot 的 `usb 0:1`（第一个 USB 存储设备、第一个分区）。工具依次执行只读盘点、
`usb start`、`size usb 0:1 /a20/kernel.elf`、受限长度的 `load` 和 CRC32 校验；只有全部通过才
执行 `bootelf -p`。若设备/分区不是 `0:1`，用独立入口明确指定：

```sh
python3 tools/ls2k0300_handoff.py boot --serial /dev/serial/by-id/YOUR_UART \
  --transfer usb --device 1:1
```

设备序号不明确时，可在串口执行 `usb start`、`usb storage` 和
`ls usb 0:1 /a20` 来确定；失败只停在文件读取阶段，不会格式化或烧写设备。

### SD / eMMC 文件读取

对于开发机已挂载的 FAT SD 分区，同样执行
`tools/a20 deploy ls2k0300 --stage-mount MOUNT_ROOT --no-console`，正常卸载后插回板卡。
已有 ext4/eMMC 分区则可自行把相同 ELF 放在 `/a20/kernel.elf`，保留所有已有文件；
主机自动 staging 入口有意只接受 FAT，串口侧 `load` 本身仍支持 FAT/ext4 自动识别。
不需要把 A20OS 写入 Linux 内核分区。

```sh
tools/a20 deploy ls2k0300 --auto-handoff --transfer mmc
```

默认 `mmc 0:1`。若该板将 TF 卡枚举为 `mmc 1`，独立入口使用 `--transfer mmc --device 1:1`。
具体检测命令是 `mmc list`、`mmc dev 0`、`mmc info` 和 `ls mmc 0:1 /a20`；
也可对 `1:1` 重复只读 `ls`，直到确认文件位置。厂商默认的 Linux `bootcmd` 使用
`mmc 0:${syspart}`，这只是出厂环境，工具不会把它当作所有板卡的硬编码事实。

### TFTP：无需拔卡

将板卡 Ethernet 接入与开发机相同的 LAN，确定开发机 IPv4 和一个未占用的板卡 IPv4。
在一个终端启动仓库自带的标准库只读 TFTP 服务器：

```sh
sudo python3 tools/ls2k0300_handoff.py serve-tftp --bind HOST_IPV4
```

此命令绑定标准 UDP 69，只提供本次包内经 SHA-256 验证的 `kernel.elf`，不提供任意主机文件，
也不写入任何文件。服务器的后续数据连接使用临时 UDP 端口；主机防火墙需允许这次板卡连接。
在另一个终端启动串口交接：

```sh
tools/a20 deploy ls2k0300 --auto-handoff --transfer tftp \
  --server-ip HOST_IPV4 --board-ip UNUSED_BOARD_IPV4
```

工具仅在 RAM 中设置 `serverip`、`ipaddr`、`filesize` 和 `autostart`，不会 `saveenv`。
网线未接、IP 不通、文件大小不符或 CRC32 不符都会停止，不会继续跳转。
厂商 `net/tftp.c` 在启用 `CONFIG_LMB=y` 时还限制下载不能越过固件预留区。

### 独立串口入口

独立入口和 `a20 --auto-handoff` 使用同一个实现；不用安装 pyserial：

```sh
python3 tools/ls2k0300_handoff.py boot \
  --serial /dev/serial/by-id/YOUR_UART --transfer usb --device 0:1
```

独立入口默认保存 `build/ls2k0300/handoff/serial.log`，失败或在提示符/启动阶段按 Ctrl-C
中断时也保留此前全部输出。`a20` 的
日志位置由实例 `target.log`/通用 console 日志规则决定。部署期间不要同时打开第二个串口终端。
只想准备文件或先审阅步骤，可以执行 `tools/a20 deploy ls2k0300 --no-console`。

## 自动化怎样判断 RAM 可用

链接入口为 `0x9000000002000000`，即 cached DMW 下的物理 32 MiB。这是本移植选择的地址，
尚未经过久久派真机验证。内核要求固件已初始化 DDR、UART0、时钟和引脚，以 PLV0 进入，
并保留 cached VSEG 9 映射；随后建立 VSEG 8/9 DMW、四级页表和 4 KiB 对齐异常入口。
当前不使用固件参数中的 DTB 指针，因此不依赖尚未验证的 Linux `bootm` 参数 ABI。

`ls2k0300_handoff.py` 不猜测 DDR 容量或直接使用 `${loadaddr}`，而是要求以下证据全部成立：

- `bdinfo` 的 DRAM 银行覆盖整个内核分配器窗口 `[2 MiB,128 MiB)`。
- `bdinfo` 必须完整输出 `lmb_dump_all`、`memory.cnt`、`reserved.cnt` 及每一行范围；
  缺失、重复、截断、零固件预留或区间长度不一致均拒绝装载。
- 同时检查 LMB 内存覆盖和预留区，并对固件栈额外保留 2 MiB；`relocaddr`、FDT、
  framebuffer 等活动指针到所属银行末端也一并保留。任何预留与内核分配器窗口重叠都会停止。
- 暂存 ELF 的地址自动从低 256 MiB DDR 的空闲区域选择，位于内核分配器窗口之外，
  64 KiB 对齐，并排除上述全部固件占用。没有合适区域就停止。
- 文件系统方式先执行 `size`，核对本地 ELF 大小后使用带字节上限的 `load`；
  传输后再次核对 `filesize` 和 CRC32，最后才执行 `bootelf -p`。

厂商源码的 `arch_lmb_reserve()` 将当前栈指针以下 4 KiB 到 `ram_top` 作为保留区；
`bdinfo` 通过 `lmb_init_and_reserve()` 打印它。工具使用额外栈余量，避免把这个 4 KiB 当成
传输过程中所有函数调用的安全上限。出厂 `99pi_wifi` 设备树还声明低银行 `[0,256 MiB)`
和高银行，并在低 240–256 MiB 保留启动参数区域；这些只用于解释预期输出，不替代现场检测。

可离线重放捕获到的完整 `bdinfo`/串口日志，检查工具将选择什么地址：

```sh
python3 tools/ls2k0300_handoff.py plan --bdinfo PATH_TO_CAPTURED_LOG
```

包工具检查 ELF64 little-endian、LoongArch `ET_EXEC`、段边界、可执行入口、重叠及 SHA-256。
厂商 `lib/elf.c` 会遍历所有 program headers，所以额外拒绝非 PT_LOAD/空 PHDR，
避免装载器把辅助 header 当作可复制内存。`kernel.bin` 不是 Linux Image，不能使用 `booti`；
也不是 uImage 或 EFI 可执行程序。

## 串口协议与失败处理

厂商默认提示符为一行末尾的 `=> `。主机逐条发送普通命令并等待完整提示符，
不用 `if/&&/$?`：`99pi_wifi_defconfig` 没有启用 Hush，不能假设 shell 条件语法可用。
没有提示符、未知命令或明确错误都会停止。

| 阶段 | 成功判据 | 失败后操作 |
| --- | --- | --- |
| prompt | 捕获 `=> ` | 工具运行时给板重上电并按 `c`；若见 `PMON>`，进入下面 PMON 分支 |
| firmware | `version` 含 U-Boot；`help bootelf` 含 `-p`；所需 `load/tftpboot`、`crc32`、`base` 可用 | 保存完整日志；不能把本包交给不存在的命令 |
| memory | 完整 DDR/LMB 表证明内核窗口和暂存区可用 | 用 `plan --bdinfo` 重现具体拒绝原因；检查日志是否截断；不要修改地址绕过检查 |
| load | `size/filesize` 等于本地 ELF；文件系统输出相同的 `N bytes read`，或 TFTP 输出 `Bytes transferred = N` | 核对 U 盘路径/分区，或 TFTP 网络；恢复后重跑即可 |
| crc | `crc32` 输出 `==> XXXXXXXX` 等于本地 ELF 的 CRC32 | 重新复制 ELF/换可靠介质，禁止继续 `bootelf` |
| boot | 出现 `[LS2K0300] stage=irq` 和 `System ready` | 保存输出；若重返 `=>` 或报错，工具报告失败，不重复跳转 |

### PMON

如果交付的是 PMON，工具只执行 `h` 捕获帮助并返回 `ls2k0300:pmon`。
在同一串口执行以下只读检测，保存输出：

```text
PMON> h
PMON> h load
PMON> h g
PMON> devls
PMON> set
```

其中 `h load` 必须说明 ELF 装载能力和支持的 URL/文件系统，`h g` 说明执行入口/参数，
`devls` 给出真实网卡和存储名字，`set` 不带参数只打印环境。不要照搬其它 Loongson/MIPS
设备的 `load -r -f`：这类选项可能用于升级固件。自动工具不升级固件；
若用户决定迁移到板厂 U-Boot，使用下面独立的人工迁移分支。

目前未找到能够确证 **久久派交付 PMON 版本** 的 ELF machine/ABI、DMW、DDR 预留和
装载后 cache 处理的公开源码契约，因此不提供自动 `load/g`。这是一条具名的固件兼容性阻塞，
不是“看到 PMON 就可当成 U-Boot 使用”。上述五条检测结果会精确给出下一版 PMON backend
需要的输入；当前可自动部署的范围明确是支持 `bootelf -p` 且提供完整 LMB 证据的原厂 U-Boot。

### PMON 用户可选：迁移到板厂已经发布的 U-Boot

这条路径会改写 SPI 固件，**不属于 `a20 deploy --auto-handoff`**。先确认实物的
TF/WiFi/Plus/红板版本与所下载包一致，保存原厂固件和恢复方式，再决定是否执行。
这里给出已有出处的具体路径，不把不同板号的二进制混用。

| 版本来源 | 下载入口 | 核验范围 |
| --- | --- | --- |
| 板厂管理员 2024-08-25 的久久派新世界发布 | [原始发布帖](https://bbs.ctcisz.com/forum.php?mod=viewthread&tid=133) → [官方 ABI2.0 包](https://share.weiyun.com/Uvi9Dcsc) | 当时 TF/WiFi 系列；包中固件名为 `ABI2.0/images/u-boot-spl-gz.bin`，须以包内型号说明匹配实物 |
| 板厂 2026-05-09 红 WiFi 板新固件 | [红板发布帖](https://bbs.ctcisz.com/forum.php?mod=viewthread&tid=23305) → [天翼云包](https://cloud.189.cn/t/UFNjMvVJRvaa)，访问码 `gz6k` | 只证明存在红 WiFi 板专用资源，不代表兼容旧 TF 或 Plus 板 |

当前环境无法读取上述云盘里的具体二进制、版本清单和校验值，所以不会自动下载、选择或刷写。
需要核对的参数包括：PCB 版本/容量、包内适用型号、固件文件 hash 和 PMON `h fload`
输出；若任何一项不符，保留原固件，不执行下面的写入命令。原系统能启动 Linux 时，先执行
`cat /proc/mtd` 找到标为 PMON/bootloader 的实际分区，再只读备份：

```sh
# 在原系统中，用 /proc/mtd 确认的节点替换 MTD_BOOTLOADER，禁止猜测 mtd0。
sudo dd if=/dev/MTD_BOOTLOADER of=pmon-backup.bin bs=64K
sha256sum pmon-backup.bin
# 通过 scp 或 U 盘把备份复制到主机，并保留板厂可用于 USB 恢复的 PMON 镜像。
```

原始发布帖中，实际完成此迁移的作者给出了[本人上板记录](https://blog.mjyai.com/2024/08/27/loongson-2k0300-flash-u-boot-install-abi2-buildroot/)。
对于与该记录相符的板号/固件，主机可用同一标准库服务器的**独立人工迁移模式**：
先对已核实型号/来源的文件执行 `sha256sum /path/to/u-boot-spl-gz.bin`，把结果记录为
`EXPECTED_SHA256`。然后启动：

```sh
sudo python3 tools/ls2k0300_handoff.py serve-firmware \
  --file /path/to/u-boot-spl-gz.bin --sha256 EXPECTED_SHA256 --bind HOST_IPV4
```

此模式只提供该文件，校验记录的 SHA-256，既不打开串口也不发送 `fload`；
**hash 只固定所选文件的身份，不能替代板厂来源/型号证明**。
板端流程是：小写 `c` 进入 PMON；用 `devls` 确认网卡是
`syn0`，用 `h fload` 确认这是该版本固件更新命令；主机 TFTP 根目录放入匹配的
`u-boot-spl-gz.bin`；设置一个未占用的同网段板 IP，然后执行：

```text
PMON> ifaddr syn0 BOARD_IPV4
PMON> fload tftp://HOST_IPV4/u-boot-spl-gz.bin
```

**`fload` 是 SPI 写入，不能把它当作可逆 RAM chainload。** 只有显示 `Programming end!`
才表示完成，`Erase end!` 尚未结束。完成后重启，按 `c` 进入新固件并核验
`version`、`bdinfo`、`help bootelf`，然后回到上面的 A20OS RAM 自动部署流程。
此迁移不需要覆盖原厂 Linux 的内核或根文件系统。

上述上板记录还给出了回退机制：把对应的原厂 PMON 恢复镜像命名为 `u-boot.bin`，放在
FAT/ext4 U 盘的 `/update/` 目录；启动时按 `m`，在确有此选项的固件菜单选择
`Update u-boot to spi flash (by usb)`。这是**同样会写 SPI 的恢复操作**，不是“刷错也能保证救回”；
必须在迁移前就备好正确型号镜像并核实菜单/厂商说明。不确定型号或当前 PMON 没有 `fload`
时，当前实现停在上面五条只读诊断，不以未经证实的升级命令继续。

## 当前能力和验收

- 已具备独立板配置、cached/uncached DMW、标量 FP 上下文、页表/异常入口、UART 中断与轮询、
  CPUCFG 计数器频率读取、ELF 包、USB/SD/TFTP 条件自动交接和失败日志。
- 默认实例为 `BRINGUP=1`，没有用户空间；验收标记是
  `System ready (bringup, no userspace)`，随后 `part ok` 并停机。
- 尚无真机记录。LIOINTC 和核内定时抢占已有实现及寄存器模型测试，真实 IRQ 投递仍待验收。GMAC、SD/eMMC、USB、显示驱动尚缺；
  `poweroff/reboot` 当前只停机。该 SoC 是单核，构建拒绝 `NR_CPUS != 1`。

## 中断驱动

板级 `liointc.c` 管理 64 路传统中断的屏蔽、触发和分发，`irqchip.c` 提供 uncached MMIO、两个固件 IRQ domain 和 CPU 级联。初始化关闭扩展路由，避免与传统路由重复投递；普通设备仅在 `request_irq()` 后使能。核内定时器在调度初始化后开启；`COOPERATIVE_BOOT=1` 可显式选择轮询。寄存器行为依据上述手册 3.5 节独立实现，并与 [Linux LIOINTC 驱动](https://github.com/torvalds/linux/blob/master/drivers/irqchip/irq-loongson-liointc.c)交叉核对。
