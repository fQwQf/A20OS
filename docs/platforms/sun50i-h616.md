# Allwinner H616 / H618 (Orange Pi Zero 2, Zero 3, Zero 2W)

`ARCH=aarch64 BOARD=sun50i-h616`

**The cleanest boot chain of any ARM board in this tree.** The SPL is built from
U-Boot source and BL31 is TF-A's `sun50i_h616` platform, which is mainline — so
nothing in the chain is a vendor blob the build cannot reproduce. Compare
Rockchip (rkbin DDR training blob), Amlogic (signed FIP), Raspberry Pi 5 (no
mainline U-Boot target at all). Boards are USD 18–35 depending on variant and
memory.

**Build-verified only. Not run on hardware.** That build claim is now
reproduced on every commit by `make check-arm-board-builds`, so the board cannot
silently stop compiling.

## Hardware facts

From upstream Linux at `551c722f40809618230001baccf219193e22fc5a`, files
`arch/arm64/boot/dts/allwinner/sun50i-h616.dtsi` and the three
`sun50i-h618-orangepi-*.dts` board files:

| Item | Value |
|---|---|
| SoC | Allwinner H616 / H618, 4× Cortex-A53 |
| GIC | `interrupt-controller@3021000`, `"arm,gic-400"` — **GICv2** |
| UART0 | `serial@5000000`, 0x400 bytes, `GIC_SPI 0` → **IRQ 32**, `"snps,dw-apb-uart"` |
| Ethernet | `ethernet@5020000` (emac0), 0x10000, `GIC_SPI 14` → IRQ 46, `"allwinner,sun50i-h616-emac0"` |
| SD | `mmc@4020000`, 0x1000, `GIC_SPI 35` → IRQ 67, `"allwinner,sun50i-h616-mmc"` |
| DRAM | 0x40000000 (no memory node in any of these board DTSs) |
| Timer | DZI 24 MHz |

A GIC SPI number is 32 + the DT value; `sun50i_h616_platform.h` has already done
that conversion.

Two of these are why this board is cheap. `"snps,dw-apb-uart"` is a 16550, which
every architecture's `console.h` already declares. `"arm,gic-400"` is GICv2,
which is exactly the `GICD_BASE`/`GICC_BASE` pair the aarch64 port already drives
— no GICv3 work. DRAM at `0x40000000` is also where the aarch64 QEMU default
already points, so the memory window needed no change.

The MAC is a Synopsys DWMAC variant (upstream `dwmac-sun8i.c`), so it is the
same IP family as `kernel/drivers/net/ls2k_gmac.c`. That is the main reason this
board is worth doing.

## Boot chain

```text
Allwinner boot ROM  →  U-Boot SPL (from source)  →  TF-A BL31 (mainline)  →  U-Boot  →  kernel
```

mainline U-Boot has `orangepi_zero2_defconfig`, `orangepi_zero3_defconfig` and
`orangepi_zero2w_defconfig`. TF-A exposes PSCI, which is what the aarch64 port
already uses.

## Scope of this port

Brings up: RAM, console UART, GICv2, PSCI `poweroff`/`reboot`.

Deliberately absent:

- **Storage.** `allwinner,sun50i-h616-mmc` is Allwinner's own controller, driven
  upstream by `sunxi-mmc.c`. A20OS's `dw_sdio.c` targets the older DesignWare
  SDIO/MMC register layout, and there is no generic MMC core to slot a new host
  into. This is the blocker for booting from a card, and it is the same reason
  the SophGo ports stop where they do — but worse, because DWCMSH at least
  belongs to a family A20OS has a driver for.
- **Ethernet.** DWMAC, so `ls2k_gmac.c` is a starting point, but it needs an
  Allwinner CCU clock-and-reset sequence first that has not been derived.
- **SMP.** `.smp` is `NULL`. Four cores exist; which of them this bootloader
  publishes has not been checked on hardware, and `porting-guide.md` requires
  `.smp` to stay NULL rather than carry a fabricated ops table.

## Deploying

`tools/a20` is the deployment tool. There is no make command here, and that is
deliberate: this board has no block driver, so there is no card to write and
nothing for `dd` to put an image on. The artifact is the kernel plus the
commands that hand it to the boot chain already on the board.

### What you get

```sh
tools/a20 package sun50i-h616
```

writes `build/sun50i-h616/handoff/`: `kernel.bin`, `uboot.cmd` with the exact lines
to run at the U-Boot prompt, and a `README.md` carrying the same instructions.

The load address is **not** written in this document or in the instance. `a20
package` reads it out of the first `PT_LOAD` header of the kernel it just built,
so a board whose linker script relocates the image cannot end up with a stale
address here.

No device tree is shipped, on purpose: U-Boot passes its own board DTB in `a1`,
and the kernel is built to be told the layout rather than to read it.

### Getting it onto the board

1. Boot the board the way its documentation says. This chain is **blob-free**,
   which is the main reason to pick this board: the H616 SPL and U-Boot are
   buildable from source with no vendor-signed blob anywhere. Keep them on the
   TF card.
2. Interrupt U-Boot's autoboot.
3. Read the kernel off the TF card:

   ```text
   mmc dev 0
   mmc read <loadaddr> 0x408000 0x8000
   ```

   `<loadaddr>` is the address `uboot.cmd` prints. The two numbers are the FAT
   partition start and a generous length; confirm both with `mmc info` on the
   board, because they are a starting point rather than a measured value.
4. Start the kernel:

   ```text
   booti <loadaddr> - <loadaddr>
   ```

   The `-` is the device tree pointer, left empty because U-Boot passes its own
   board DTB in `a1` itself.

### Verifying

```sh
tools/a20 deploy sun50i-h616     # build, package, print the commands, then check
tools/a20 console sun50i-h616    # just watch and check an already-running board
```

The console is `/dev/ttyUSB0` at 115200. Override the node if your adapter
enumerates differently — `ls /dev/ttyUSB*` before plugging in and after.

**On this architecture the only boot evidence is `System ready`.** There is no
`[FDT]` line: only riscv64 and loongarch parse a device tree, and the aarch64
port has no DT-based RAM narrowing, so `console_check` waits for that one string
and nothing else. `System ready` is printed by `kernel/main.c` and means the
kernel reached userspace.

### The load address is the first thing to check

`KERNEL_ENTRY` is a compile-time constant. The H616 SPL loads at `0x40000000`
and U-Boot's `loadaddr` decides where the kernel actually lands. If the two
disagree the kernel jumps to an address it was not linked for, and the board
hangs before the first `printf`.

### If it does not boot

Ordered by what actually fails first.

1. **Nothing on the console.** Wrong UART or pinmux. The boot chain releases
   the UART clock, so silence usually means the firmware did not run.
2. **U-Boot banner, then silence.** The load address, above. This is the first
   value to check on this board.
3. **`mmc read` reads nothing.** Confirm the partition start and length with
   `mmc info` on the board; the offsets in the instance are a starting point, not
   a measured value.

## Two things nobody can settle without the board

1. **`KERNEL_ENTRY` is a compile-time constant and unverified.** The H616 SPL
   loads at `0x40000000`; U-Boot's `loadaddr` decides where the kernel lands. If
   the board hangs before the first `printf`, this is the first value to check.
2. **DRAM size.** No board DTS declares a memory node — U-Boot passes the layout —
   and the aarch64 port has no DT-based RAM narrowing the way riscv64's
   `riscv64_memory_init()` does. `PHYS_MEMORY_END = 0x80000000` is a 1 GiB
   *window*, not a measurement. A 2 GiB Zero 3 needs it raised, or the allocator
   will hand out a page that does not exist.

Both are recorded in `sun50i_h616_platform.h` at the point where they matter.

## Before claiming hardware verification

1. Build, compare U-Boot's load address against `KERNEL_ENTRY`, and confirm the
   real DRAM size against `PHYS_MEMORY_END`.
2. Boot and confirm the console banner. The Zero 2 and Zero 3 route the debug
   UART to header pins 8/9 (uart0); the Zero 2W uses a different header — check
   which you have before assuming 115200 on the first pin.
3. Record the acceptance table from `porting-guide.md`.
