# x86_64 PC 兼容机

`ARCH=x86_64 BOARD=x86_64-pc` 面向真实的 PC 兼容硬件：翻新瘦客户机（Dell Wyse 3040/5070、HP t630、
Lenovo Tiny）、基于 Intel N100/N305/J4125 或 AMD 嵌入式 V 系列的无风扇迷你主机，以及办公台式机。

它不绑定某一个 SKU。这块板真正做的事是停止假装机器是 QEMU：下面三处改动各自把一条写死的 QEMU 事实，
换成从正在运行的固件里读到的值。

## 为什么需要单独的板级

QEMU q35 板对自己的机器并没有说错——它错在**其他所有**机器上，有三处，而且每一处都必须在架构层修好
才能让任何 PC 启动。这些修复被移到板级契约之后，架构层就不再需要知道板子的名字。

## 改了什么，还剩什么

| 原来 | 现在 | 状态 |
|---|---|---|
| ECAM 基址写死为 `0xB0000000`（q35 MMCONFIG） | 从 ACPI `MCFG` 偏移 72 读取 | 完成 |
| 完全不支持 PCIe 之前的机器 | ECAM 窗口里没有 host bridge 时回退到 `0xCF8`/`0xCFC` | 完成 |
| PCI INTx 用一个在真实芯片组上错误的扁平 GSI 公式 | 读取并求值 ACPI `_PRT`，不做任何猜测 | **需要逐芯片组确认** |
| 关机时向固定端口写固定值 | `firmware_acpi_poweroff()` 读 FADT PM1a，先写规范的 S5 值再写 QEMU 兼容值 | QEMU 下完成，**真机未验证** |
| — | 只支持 MSI-X（capability `0x11`）；普通 MSI（`0x05`）虽有 `#define` 但未被使用 | **未实现——只有 MSI 的设备（AHCI/NVMe/xHCI/rtl8139）仍走 INTx 或轮询** |
| — | 越过 bus 0 的 `_PRT` 下钻（桥树）、i440fx PIRQ link 写入 | **未实现——桥后设备保持轮询** |
| 命令行只从 QEMU `fw_cfg` 读取 | 先读 multiboot info 偏移 16，再回退 `fw_cfg` | 完成 |
| 无显示输出 | — | **未实现** |
| `e1000` 只覆盖 82540EM/82545EM/82546EB/82541PI/82574L | `rtl8139` 额外认领 10ec:8139（PCI class `0x020000`） | **部分——只覆盖一个 Realtek ID** |
| — | 其他 Realtek ID（8139B/8139C 超集行为、8168/8169、8125），以及任何"按 class 回退绑定网卡" | **未实现** |

### ACPI MCFG

2011 年之后的芯片组把 ECAM 放在 `0xE0000000` 或 MCFG 指定的位置；只有 QEMU q35 用 `0xB0000000`。在此
之前，真实硬件上的每次配置读取都返回 `0xffffffff`，根本找不到任何 PCI 设备。`firmware_acpi_mcfg_base()`
读取该表，板级把结果交给 `arch_pci_host_init()`。总线范围也取自同一张表。

### PCI INTx 路由——真实硅片上仍未确认

设备的 INTx 线最终落在哪条中断上，是固件的决定，发布在 ACPI DSDT 的 per-bus `_PRT` 路由表里，在 i440fx
上则编程进芯片组的 PIRQ link。这里没有可套用的公式。

本板此前靠 host bridge id 识别 q35，其他一律返回 `-1`，于是每个真实芯片组都退回轮询：AHCI 与 NVMe 能用，
但只是轮询速度。这诚实但慢。后来它又"改进"为接受板级给出的 GSI 基址并计算扁平 swizzle——那比回退更糟，
因为猜错的 GSI 不只是帮不上忙：固件通常已经把那条 IOAPIC 表项编程给了别的设备，猜出来的值会把别人拥有
的线重定向走。而启动日志还把那个基址打印得像一次测量。

现在的情况：

* `kernel/arch/x86_64/platform/acpi_dsdt.c` 求值读取 `_PRT` 所需的 DSDT 子集，并把 BDF 映射到 GSI。
  它**失败即关闭**：任何未实现的 opcode、任何走不通的 package、任何未在表中命名的设备，都返回"没有 GSI"，
  让驱动继续轮询。它从不返回猜测值。
* `arch_pci_intx_irq()` 先问 DSDT。只有它拒绝时，才考虑那台不需要固件就能知道接线的机器——QEMU 的 q35，
  根总线 INTx 经 `20 + ((dev + pin - 1) & 3)` 落到 GSI 20-23，这个映射是对着模拟器实测出来的。
* 启动日志会说明是谁回答的：`(ACPI _PRT)` 或 `(q35 swizzle)`。

**这在任何真实芯片组上都还没有确认过。** `_PRT` 求值器只对着 QEMU 的最小 DSDT 跑过，而 QEMU 也会拒绝它——
q35 门禁展示的是 swizzle，不是 `_PRT`。在真实硬件上，这个解释器一次都没有被执行过。请把启动日志里的
`[PCI] INTx ...` 当作一个声明而不是测量，并在相信数据路径之前查 `/proc/interrupts`。

两条已知限制，都是刻意保留的：

* **只处理 bus 0。** `dsdt_scope_for_bus()` 只回答根总线。桥后设备需要下钻桥树才能找到它所在总线的
  `_PRT`，这没有实现。这类设备退回轮询。
* **不编程 PIRQ。** i440fx 上路由还存在于 PIIX3 的 PIRQ link 寄存器里。内核只读固件设置的值，从不写回，
  因此固件把 link 留成关闭的设备仍停留在轮询路径上。

### PCIe 之前的机器（i440fx）

没有 ECAM 窗口的机器——i440fx——配置空间仍在传统的 `0xCF8`/`0xCFC` 端口后面，而编译期写死的 q35 地址
在那里什么也没有。检测方式是在该窗口 00:00.0 处探测 host bridge，而不是去找某个特定的错误值：
`0xffffffff` 是"窗口已解码但没有设备"，`0x00000000` 是"窗口根本不存在"，两者都必须拒绝。
`smoke-pci-i440fx` 覆盖这条路径，见 `docs/testing-gates.md`。

### 关机——ACPI S5 与一个 QEMU 怪癖

`pc_poweroff()` 过去向固定端口写固定值，那在 QEMU 上是 q35 的 S5 寄存器，在真实芯片组上什么也不是。
现在它走 `firmware_acpi_poweroff()`：从 FADT 读取 PM1a 控制块（偏移 52）、其宽度与支持的睡眠状态
（偏移 116），然后写 `SLP_TYP=5 | SLP_EN`——ACPI 正确的软关机请求。

FADT 在两种签名下都能找到：`FACP`（ACPI 2.0 及以后）与 `FADT`（revision 1，较老固件仍在用）。

**唯一刻意的偏离。** QEMU 不实现 ACPI 的 S5 编码。在 `hw/acpi/core.c` 里，`acpi_pm_cnt_write()` 按睡眠
类型分支，只在值为 `0` 时关机；`5` 落到一个什么都不做的分支。在 QEMU 上有效的值是 `SLP_TYP=0`
（`0x2000`），而它在真实硬件上是**保留值**。因此 `firmware_acpi_poweroff()` 先写规范值，短暂自旋让真实
芯片组有机会响应，再写 QEMU 兼容值。真实硬件在第二次写之前就已经关机；QEMU 下第一次是 no-op，第二次生效。
代码里把这个回退明确标注为模拟器怪癖，因为它确实就是。

**未在真实硅片上验证。** 只有 QEMU 那一半被执行过。如果第一次写没能让真机关机，第一个要查的是 FADT
的 PM1a 块地址或宽度——而不是编码，编码恰恰是有规范可依的部分。

### 内核命令行

`firmware_bootargs()` 只读 QEMU 的 `fw_cfg` 设备，而真实机器上没有它，于是返回空，所有 `a20.*` 旋钮都
不可达。Multiboot v1 无论 GRUB 以 BIOS 还是 UEFI 方式加载内核，都会把命令行放在 info 块偏移 16 处，
因此现在先读这里。两种探测都会出现在日志里：

```text
[BOOTARGS] multiboot cmdline='...'
[FW_CFG] no QEMU fw_cfg, using fallback bootargs
```

GRUB2 的 `multiboot`（v1）模块在 UEFI 与 BIOS 下都能用，因此一台纯 UEFI 的 2025 年迷你主机也能启动：
`grub-install --target=x86_64-efi`，然后在 `grub.cfg` 里写 `multiboot /boot/kernel.elf`。

树里现在也有一个 x86_64 UEFI loader（`kernel/boot/uefi/x86_64_loader.c`，构建为 `BOOTX64.EFI`）。在适用
场合它是更好的产物：它把 GRUB 2.12 会丢掉的 ACPI RSDP 交给内核，而没有 RSDP 就没有 MCFG，PCI 就会去读
一个没有任何设备的写死窗口。它目前按 `qemu-virt-x86_64` 板的内存地图构建，并由 `instances/vbox-x86_64.toml`
部署；因此对于内存布局无法预先知道的板子——也就是本页涉及的所有机器——GRUB ISO 仍是那条路线。

### 没有显示

`kernel/drivers/gpu/` 有 virtio-gpu、VMware SVGA 与一个 framebuffer 抽象。没有传统 VGA `0xB8000` 文本
驱动，没有 VBE，也没有 EFI GOP 路径，因此在真实硬件上内核**只有串口**。

这是最该先解决的现实问题：大多数瘦客户机没有 RS-232 接口。HP t630 就完全没有。你需要把 USB-TTL 适配器
焊到内部排针上，或者找到你这型号上那个没有文档的接口。为此留出半天时间，并先读板子的维修手册——引脚
定义并不统一。

## 部署

部署工具是 `tools/a20`。这是唯一一块从真实介质启动的新板，因为它有块驱动（AHCI），GRUB 也能启动
multiboot 内核——所以部署路径就是常规那套：构建 ISO、写进 U 盘、启动。

### 前置依赖

救援 ISO 是本仓库里唯一需要 GRUB 工具链的东西：

```sh
sudo apt-get install grub-pc-bin grub-efi-amd64-bin xorriso
```

`grub-mkrescue` 调用 `xorriso`，没有它打包会以 `grub-mkrescue: 未找到 xorriso` 中止。riscv64 与 aarch64
板都不需要这些。

### 你会得到什么

```sh
tools/a20 package x86_64-pc
```

写出 `build/x86_64-pc/a20os-rescue.iso`。这个路径刻意放在 per-build 目录之外：实例必须在 `boot_media`
里命名这个文件，`a20 deploy` 才会去写它；而 per-build 目录名带有 arch、board、ABI 与 variant，清单里
没法指向它。

### 写入与启动

```sh
tools/a20 deploy x86_64-pc
```

完成构建、打包、把 ISO 写到 `media_device`，然后接上控制台检查结果。想手工操作，或写到另一支 U 盘：

```sh
# 先确认是哪支盘；写之前核对容量
lsblk
sudo dd if=build/x86_64-pc/a20os-rescue.iso of=/dev/sdX bs=4M status=progress
sync
```

`a20 deploy` 拒绝写入已挂载的设备，也拒绝名字与镜像不匹配的设备。这个保护正是它优于 `dd` 的理由：在
一台双盘机器上把 `/dev/sda` 敲错，不是可恢复的错误。

然后启动：进入固件启动菜单选 U 盘，或按你机器固件的一次性启动键。

### BIOS、UEFI，以及本页为什么仍用 GRUB

ISO 里 `grub.cfg` 的 `multiboot /boot/kernel.elf` 负责加载内核，而 GRUB 的 multiboot v1 模块无论 GRUB
自己是由 BIOS 还是由 UEFI boot services 启动都能用。这一点很重要，因为 2025 年的瘦客户机大多是纯 UEFI
且没有 CSM 选项。因此启动这个 ISO 不是"缺少 BIOS 支持"的权宜之计，而是同时覆盖两种固件风格的路线。

树里的 x86_64 UEFI loader 也能覆盖纯 UEFI 的情况，并且对 `qemu-virt-x86_64` 板已经这样做了，但它是按
那块板的内存地图构建的。本页讲的是布局无法预先知道的机器，所以这里仍以 ISO 为产物。

### 验证

```sh
tools/a20 console x86_64-pc
```

控制台是 `/dev/ttyUSB0`，115200。**大多数瘦客户机没有 RS-232 接口**——HP t630 完全没有——所以要有把
USB-TTL 适配器焊到内部排针上的准备，`console_check` 才可能通过。实例里的 `serial` 是常见 USB-TTL 节点，
只是占位：先填上你真实的节点，再相信一次失败。

只有出现下面这些行才算启动成功：

| 行 | 证明什么 |
|---|---|
| `[BOOTARGS] multiboot cmdline` | multiboot 命令行路径带上了 `a20.*` 设置 |
| `[RAM] usable ...` | 内存地图被解析并找到了 RAM |
| `System ready` | 内核进入了用户态 |

这里刻意**没有 `[FDT]` 行**。只有 riscv64 与 loongarch 解析 device tree；这里是传统的 BIOS/UEFI 固件，
没有 DT 可解析，`[BOOTARGS]` 与 `[RAM]` 才是 x86_64 上真实存在的依据。multiboot 那行是最重要的回归
保护：真实机器上没有 `fw_cfg`，因此只有 multiboot 那行能带上 `a20.*` 设置；一台缺了它还能启动的机器，
就是设置静默失效的机器。

### Bring-up 顺序

按 `porting-guide.md`：从 `NR_CPUS=1` 开始，确认串口与 RAM，再提高 CPU 数。在 `qemu-virt-x86_64` 之外的
板子上用 `NR_CPUS>1` 需要 `ALLOW_UNVERIFIED_SMP=1`：

```sh
tools/a20 package x86_64-pc -- NR_CPUS=4 ALLOW_UNVERIFIED_SMP=1
```

### 如果启动不了

1. **启动菜单里看不到 U 盘。** 写到了错误的设备，或机器固件只在你没选的那种模式下从 USB 启动。
2. **出现 GRUB，但内核始终不出现。** GRUB 读不出 ISO 里的内核：确认 ISO 写完整（与源文件 `cmp`）。
3. **内核启动了，但控制台没有输出。** 串口接线不对，或没接 USB-TTL 适配器（见上）。
4. **没有 `[BOOTARGS]` 行。** multiboot 命令行路径没跑，`a20.*` 设置没有到达内核。这是真 bug，不是接线
   问题。
5. **没有 `[RAM] usable`。** 内存地图没被解析。没有它就没有 RAM 范围，之后的任何东西都不可能工作。

## 内存地图注记

RAM 来自 multiboot 内存地图而不是板级声明，因此同一份镜像适配任意内存大小。两个窗口值得知道：

- `X86_DIRECT_MAP_END` 是 2 GiB，PCI MMIO 窗口在 3 GiB，因此 2–4 GiB 的物理区间被刻意留空不映射。一台
  8 GB 机器会报告 2 GiB 低端加 4–8 GiB 的高端块：6 GiB 可用、2 GiB 保留。
- 4 GiB 以上，RAM 按整 1 GiB 块映射，全有或全无，因为一个只含部分 RAM 的 1 GiB 页会让其中的其他内容
  变成可缓存。
