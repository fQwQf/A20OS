# x86_64 PC-compatible machines

`ARCH=x86_64 BOARD=x86_64-pc` targets physical PC-compatible hardware:
refurbished thin clients (Dell Wyse 3040/5070, HP t630, Lenovo Tiny), fanless
mini PCs on Intel N100/N305/J4125 or AMD embedded V-series, and office boxes.

It is not tied to one SKU. What the board actually does is stop pretending the
machine is QEMU: the three changes below each replace a hardcoded QEMU fact
with something read from the firmware that is actually running.

## Why a separate board at all

The QEMU q35 board was not wrong about its own machine — it was wrong about
every *other* machine, in three ways that all had to be fixed in the arch layer
before any PC could boot. This commit moves those fixes behind the board
contract so the arch layer learns no board names.

## What changed, and what is left

| Was | Now | Status |
|---|---|---|
| ECAM base hardcoded to `0xB0000000` (q35 MMCONFIG) | read from ACPI `MCFG` offset 72 | done |
| No pre-PCIe support at all | `0xCF8`/`0xCFC` fallback when the ECAM window holds no host bridge | done |
| PCI INTx used a flat GSI formula that was wrong on real chipsets | ACPI `_PRT` is read and evaluated; nothing is guessed | **needs per-chipset confirmation** |
| Command line read only from QEMU `fw_cfg` | multiboot info offset 16 first, `fw_cfg` fallback | done |
| No display output | — | **not implemented** |
| `e1000` covers only 82540EM/82545EM/82546EB/82541PI/82574L | `rtl8139` additionally claims 10ec:8139 (PCI class `0x020000`) | **partial — one Realtek ID only** |
| — | other Realtek IDs (8139B/8139C superset behaviour, 8168/8169, 8125), and any "NIC by class" fallback binding | **not implemented** |

### ACPI MCFG

A 2011-onward chipset places ECAM at `0xE0000000` or wherever MCFG says; only
QEMU q35 uses `0xB0000000`. Before this change every config read on real
hardware returned `0xffffffff` and no PCI device was found at all.
`firmware_acpi_mcfg_base()` reads the table and the board hands the result to
`arch_pci_host_init()`. The bus range comes from the same table.

### PCI INTx routing — still unconfirmed on real silicon

Where a device's INTx line lands is a firmware decision, published in the ACPI
DSDT as a per-bus `_PRT` routing table and, on i440fx, programmed into the
chipset's PIRQ links. There is no formula for it.

This board previously identified q35 by host bridge id and returned `-1` for
everything else, so every real chipset fell back to polling: AHCI and NVMe
worked, at polled speed. That was honest but slow. It then "improved" on that by
accepting a GSI base from the board and computing a flat swizzle — which was
worse than the fallback, because a guessed GSI does not merely fail to help:
firmware has usually already programmed that IOAPIC entry for another device, so
the guess redirects a line somebody else owns. The boot log printed the base as
though it were a measurement.

What is there now:

* `kernel/arch/x86_64/platform/acpi_dsdt.c` evaluates the DSDT subset needed to
  read `_PRT` and maps a BDF to its GSI. It **fails closed**: any opcode it does
  not implement, any package it cannot walk, any device not named in the table,
  and it returns "no GSI" so the driver keeps polling. It never returns a guess.
* `arch_pci_intx_irq()` asks the DSDT first. Only if that declines does it
  consider the one machine whose wiring is known without firmware — QEMU's q35,
  where root-bus INTx goes to GSI 20-23 via `20 + ((dev + pin - 1) & 3)`,
  verified empirically against the emulator.
* Boot log says which one answered: `(ACPI _PRT)` or `(q35 swizzle)`.

**This has not been confirmed on any physical chipset.** The `_PRT` evaluator has
only ever run against QEMU's minimal DSDT, and QEMU declines it too — the q35
gate shows the swizzle, not `_PRT`. On real hardware the interpreter has never
been exercised at all. Treat `[PCI] INTx ...` in a boot log as a claim, not a
measurement, and check `/proc/interrupts` before believing a data path.

Two known limits, both deliberate:

* **Bus 0 only.** `dsdt_scope_for_bus()` answers for the root bus. A device
  behind a bridge needs the bridge tree descended to find the `_PRT` of the bus
  it sits on; that is not implemented. Such devices fall back to polling.
* **No PIRQ programming.** On i440fx the routing also lives in the PIIX3 PIRQ
  link registers. The kernel reads what firmware set but never writes it, so a
  device whose link firmware left disabled stays on the polling path.

### Pre-PCIe machines (i440fx)

A machine with no ECAM window — i440fx — keeps config space behind the legacy
`0xCF8`/`0xCFC` ports, and the compiled-in q35 address holds nothing. Detection
probes the window for a host bridge at 00:00.0 rather than looking for one
specific wrong value: `0xffffffff` is what a decoded window with no device
reads, `0x00000000` is what a window that is not there reads, and both must be
rejected. `smoke-pci-i440fx` covers this; see `docs/testing-gates.md`.

### Poweroff — ACPI S5, and a QEMU quirk

`pc_poweroff()` used to write a fixed value to a fixed port, which is the q35
S5 register on QEMU and nothing at all on a real chipset. It now goes through
`firmware_acpi_poweroff()`, which reads the FADT for the PM1a control block
(offset 52), its width, and the supported sleep states (offset 116), then writes
`SLP_TYP=5 | SLP_EN` — the ACPI-correct soft-off request.

The FADT is found under either signature: `FACP` (ACPI 2.0 and later) and `FADT`
(revision 1), which older firmware still uses.

**The one deliberate deviation.** QEMU does not implement ACPI's S5 encoding. In
`hw/acpi/core.c`, `acpi_pm_cnt_write()` switches on the sleep type and shuts down
only for `0`; `5` falls through to a case that does nothing at all. The value
that works on QEMU, `SLP_TYP=0` (`0x2000`), is *reserved* on real hardware. So
`firmware_acpi_poweroff()` writes the spec-correct value, spins briefly to let a
real chipset act on it, then writes the QEMU-compatible one. On real hardware the
machine is already off before the second write; under QEMU the first is a no-op
and the second takes effect. The fallback is labelled as an emulator quirk in the
code because that is exactly what it is.

**Not verified on real silicon.** Only the QEMU half has been exercised. If the
first write does not power off a real machine, the FADT PM1a block address or
width is the first thing to check — not the encoding, which is the part that is
actually specified.

### Kernel command line

`firmware_bootargs()` read only QEMU's `fw_cfg` device, which does not exist on
a physical machine, so it returned empty and every `a20.*` knob was
unreachable. Multiboot v1 puts the command line in the info block at offset 16
whichever way GRUB loaded the kernel, BIOS or UEFI, so that is now read first.
Both probes appear in the log:

```text
[BOOTARGS] multiboot cmdline='...'
[FW_CFG] no QEMU fw_cfg, using fallback bootargs
```

GRUB2's `multiboot` (v1) module works under UEFI as well as BIOS, so a UEFI-only
2025 mini PC still boots: `grub-install --target=x86_64-efi` followed by
`multiboot /boot/kernel.elf` in `grub.cfg`.

There is now an x86_64 UEFI loader in the tree (`kernel/boot/uefi/x86_64_loader.c`,
built to `BOOTX64.EFI`), and where it applies it is the better artifact: it hands
the kernel the ACPI RSDP that GRUB 2.12 drops, and with no RSDP there is no MCFG,
so PCI reads a hardcoded window that holds no devices. It is currently built
against the `qemu-virt-x86_64` board's memory map and deployed by
`instances/vbox-x86_64.toml`, so the GRUB ISO stays the route for a board whose
memory layout is not known in advance — which is every machine this page is about.

### No display

`kernel/drivers/gpu/` has virtio-gpu, VMware SVGA and a framebuffer
abstraction. There is no legacy VGA `0xB8000` text driver, no VBE and no EFI
GOP path, so the kernel is **serial-only** on real hardware.

This is the practical thing to sort out first: most thin clients do not expose
an RS-232 connector. HP t630 has none. You will need to solder a USB-TTL
adapter onto the internal header, or find the undocumented one on your model.
Budget an afternoon for this and read the board's service manual first — the
pinout is not standardised.

## Deploying

`tools/a20` is the deployment tool. This is the one new board that boots from
real media, because it has a block driver (AHCI) and GRUB can start the multiboot
kernel — so the deployment path is the ordinary one: build an ISO, write it to a
USB stick, boot.

### Prerequisites

The rescue ISO is the only thing in this tree that needs GRUB's tooling:

```sh
sudo apt-get install grub-pc-bin grub-efi-amd64-bin xorriso
```

`grub-mkrescue` calls `xorriso`, and without it packaging stops with
`grub-mkrescue: 未找到 xorriso`. No riscv64 or aarch64 board needs these.

### What you get

```sh
tools/a20 package x86_64-pc
```

writes `build/x86_64-pc/a20os-rescue.iso`. The path is deliberately outside the
per-build directory: an instance has to name this file in `boot_media` to have
`a20 deploy` write it, and the per-build directory's name carries the arch,
board, ABI and variant, so it cannot be pointed at from a manifest.

### Writing it and booting

```sh
tools/a20 deploy x86_64-pc
```

builds, packages, writes the ISO to `media_device`, and then attaches the console
to check the result. To do it by hand, or to a different stick:

```sh
# find the stick first; check the size before writing anything
lsblk
sudo dd if=build/x86_64-pc/a20os-rescue.iso of=/dev/sdX bs=4M status=progress
sync
```

`a20 deploy` refuses to write a mounted device, and refuses one whose name does
not match the image it was given. That guard is the reason to prefer it over
`dd`: a mistyped `/dev/sda` on a machine with two disks is not a recoverable
mistake.

Then boot it: enter the firmware boot menu and pick the USB stick, or press the
key your machine's firmware uses for one-time boot.

### BIOS, UEFI, and why this page still uses GRUB

`multiboot /boot/kernel.elf` in the ISO's `grub.cfg` is what loads the kernel,
and GRUB's multiboot v1 module works whether GRUB itself was started by BIOS or
by UEFI boot services. That matters because most 2025 thin clients are
UEFI-only with no CSM option. Booting this ISO is therefore not a workaround for
missing BIOS support; it is the route that covers both firmware styles.

The tree's x86_64 UEFI loader would cover the UEFI-only case too, and does so
for the `qemu-virt-x86_64` board, but it is built against that board's memory
map. This page is about machines whose layout is not known in advance, so the
ISO stays the artifact here.

### Verifying

```sh
tools/a20 console x86_64-pc
```

The console is `/dev/ttyUSB0` at 115200. **Most thin clients have no RS-232
connector** — the HP t630 has none at all — so expect to solder a USB-TTL
adapter onto the internal header before `console_check` can pass. `serial` in the
instance is the common USB-TTL node and is a placeholder: fill in your real one
before trusting a failure.

A boot counts only if these lines appear:

| Line | What it proves |
|---|---|
| `[BOOTARGS] multiboot cmdline` | the multiboot cmdline path carried the `a20.*` settings |
| `[RAM] usable ...` | the memory map was parsed and RAM was found |
| `System ready` | the kernel reached userspace |

There is deliberately **no `[FDT]` line here.** Only riscv64 and loongarch parse
a device tree; this is legacy BIOS/UEFI firmware with no DT to parse, and the
`[BOOTARGS]` and `[RAM]` lines are the evidence that actually exists on x86_64.
The multiboot line is the regression guard that matters most: on a real machine
`fw_cfg` is absent, so only the multiboot line can carry `a20.*` settings, and a
machine that boots without it is a machine whose settings silently did nothing.

### Bring-up order

Follow `porting-guide.md`: start with `NR_CPUS=1`, confirm serial and RAM, then
raise the CPU count. `NR_CPUS>1` on a board other than `qemu-virt-x86_64` needs
`ALLOW_UNVERIFIED_SMP=1`:

```sh
tools/a20 package x86_64-pc -- NR_CPUS=4 ALLOW_UNVERIFIED_SMP=1
```

### If it does not boot

1. **The stick does not appear in the boot menu.** It was written to the wrong
   device, or the machine's firmware only boots USB in a mode you did not select.
2. **GRUB appears but the kernel never does.** GRUB cannot read the kernel off
   the ISO: check that the ISO was written completely (`cmp` it against the
   source file).
3. **Kernel starts, no console output.** Wrong serial wiring or no USB-TTL
   adapter, above.
4. **`[BOOTARGS]` line absent.** The multiboot cmdline path did not run, so no
   `a20.*` setting reached the kernel. This is a real bug, not a wiring problem.
5. **`[RAM] usable` absent.** The memory map was not parsed. Without it there are
   no RAM ranges, so nothing after this can work.

## Memory map notes

RAM is discovered from the multiboot memory map, not declared by the board, so
the same image fits any RAM size. Two windows are worth knowing about:

- `X86_DIRECT_MAP_END` is 2 GiB and the PCI MMIO window sits at 3 GiB, so the
  2–4 GiB physical range is deliberately left unmapped. An 8 GB machine
  reports 2 GiB low plus the 4–8 GiB high chunks: 6 GiB usable, 2 GiB reserved.
- Above 4 GiB, RAM is mapped in whole 1 GiB chunks, all-or-nothing, because a
  partially-RAM 1 GiB page would make whatever else is in it cacheable.

## Verification status

**Build-verified and emulator-verified; not hardware-verified.**
`make check-x86_64-pc-build` rebuilds this board on every commit, and
`smoke-x86_64` passes and shows both bootargs probes.

What has been run and observed, as distinct from what is only argued:

| Area | State | Evidence |
|---|---|---|
| Build | verified | `check-x86_64-pc-build` |
| Boot, cmdline, RAM map | verified under QEMU | `smoke-x86_64` |
| PCI enumeration via MCFG | verified under QEMU | `smoke-pci-bridge` |
| PCI enumeration without ECAM | verified under QEMU | `smoke-pci-i440fx` |
| ACPI S5 poweroff | verified under QEMU only | QEMU's PM1a handling differs from silicon — see above |
| INTx `_PRT` evaluation | **never executed** | QEMU's DSDT is minimal and declines it; the q35 path takes the swizzle |
| INTx delivery on real silicon | **not tested** | no physical machine |
| Multiprocessor bring-up | **not tested** | no physical machine |

The two untested rows are the ones that matter for a real-hardware claim. The
`_PRT` interpreter has never once run on real firmware, and nothing has confirmed
that a physical chipset delivers a single interrupt on a line this kernel
routed. See the acceptance table in `porting-guide.md` for what a real-hardware
claim requires.
