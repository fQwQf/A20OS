## Per-workload result

`acquires` / `spins` / `max_spins` are the workload window only: the counters are zeroed with `echo reset > /proc/a20/lock_contention` immediately before the workload command and read immediately after, so boot-time traffic is excluded by construction rather than subtracted after the fact. `Control-window` is the same counters between the reset and the first read -- the floor the workload numbers sit on.

**Noise discipline.** `docs/server-readiness.md` records repeated runs of one 4-core workload spanning 0 to ~920024 spins, and this table's own max-min spread is the honest resolution limit for every cell below. A post-change median that differs from the baseline median by less than that cell's max-min spread is **not resolvable** at this sample size and must be written as such rather than claimed.

## Noise band used for the verdict

The verdict rule is the one the baseline itself states (`lock-baseline.md:23`):
**a post-change median differing from the baseline median by less than that
baseline cell's own max-min spread is not resolvable.** That per-cell spread is
the noise bandwidth recorded in the baseline. As a second, stricter check the
after round's own max-min spread is reported too; the verdict column follows the
baseline's rule, and the last column flags where the two rules disagree.

Note on the roadmap's preferred bandwidth: `docs/roadmap/lock-serialization-split.md`
§5 asks for a "same binary, same image, same session" repeat set (3 extra runs
per workload on the B1 baseline) to be the bandwidth source. **No such repeat set
exists** -- `docs/measured/` holds only `lock-baseline.md`/`.json` and
`lock-after.md`/`.json`, and `lock-baseline.md` contains no B1 section. The
per-cell baseline spread is therefore the only recorded bandwidth available, and
it is used here. The `server-readiness.md` 0-~920024 figure is not used as a
numeric threshold, per the same §5 note.

## Why the four `proc` -> `tasklist` rows must not be read as a contention win

The delta is real as a number and it does exceed the baseline's noise band. It
is not evidence that contention fell, for three reasons visible in the tree:

1. **The counter now measures less.** Baseline `proc` was one global lock
   covering task-list membership, per-task scheduling state, and runqueue
   membership. `tasklist` covers only the first (`kernel/include/core/lock.h`
   header comment). The per-task state lock `task->park_lock` took over the
   second. That is why baseline `mm_stress` shows 24313 acquires and after shows
   7: the hot park/yield/idle paths simply no longer take the *registered* lock.
2. **The lock that absorbed the work has no counter channel.** `park_lock` is
   referenced in 359 places under `kernel/` and is passed to
   `lock_counters_register()` nowhere -- the only registrations in the tree are
   `tasklist`, `runq`, `net_bucket_*`, `lwip`, `block_cache`, `page_cache`,
   `dcache`. Spins that moved from `tasklist` into `park_lock` are invisible to
   `/proc/a20/lock_contention`. So the measured drop is at least partly a
   relabelling, and the size of the unmeasured remainder is unknown.
3. **`sched_stress` and `futex_stress` show the channel going silent, not
   contention vanishing.** All five `sched_stress` runs report 0 acquires and 0
   spins for `tasklist`; four of five `futex_stress` runs report 0. A lock that
   is never acquired cannot be contended, but that is a statement about the
   counter, not about the scheduler.

`impl-notes-proc.md` and `docs/archive/process-lock-split-audit.md` were not
consulted for this section; the mapping above is taken from the registration
call sites and the `kernel/include/core/lock.h` header comment.

`net_bucket_0..31` are registered in this tree and absent from the baseline, so
the net split has no before/after comparison available in this repository. This
is the gap §5.1 of `docs/roadmap/lock-serialization-split.md` anticipated: it
requires a **B1** baseline -- registration patch applied, splitting *not* yet

RUNS is likely a precondition for a net-side claim, not an optional extra.

## What would be needed to make a claim

1. Register `task->park_lock` (and the per-CPU `g_cpu_switch_out` publication, if
   it is a separate lock) with `lock_counters_register()`, then re-measure both
   phases. Without a counter on `park_lock` the proc-side delta cannot be
   interpreted.
2. Collect the B1 baseline the roadmap §5.1 specifies -- registration patch
   only, no split -- so `net_bucket_*` and `slab0..6` have a before image.
3. Register the 7 slab cache locks so the `slab` name the roadmap tracks
   actually exists; it is still absent in both phases.
4. If a stricter bandwidth is wanted, add the same-binary repeat set §5 asks for;
   at 5 runs under TCG several active cells already sit inside their own spread.
