# A20OS 1.0：子系统稳定性与发布契约

决策日期：2026-10-13。本文是开发与验收计划，不是 1.0 已实现或已发布的声明。
Rust 迁移已覆盖多个复杂状态、生命周期、回滚与并发职责；当前批次的范围和证据见 [当前模块状态索引](../status/current/module-status-2026-10-19.md)。仍需按各子系统契约完成适用的功能、失败路径、集成和性能验收；简单 dispatch、glue、byte-copy 与热点 C 原语可保留。生产 C 基线统计仅作历史工作量参考，不构成迁移比例或删 C 门槛。G0 比较工具是手动执行入口，不能单独证明 C0/Cn 行为或完成 1.0 验收。

## 1. 交付目标

1.0 同时完成三件事：修复现有缺陷、完成已经推进开发的子系统、验证功能与稳定性。
只让已有 smoke 变绿、只迁移语言、只启动一个演示程序，都不能作为子系统开发完成。
对大量共享状态、争用、复杂引用生命周期、取消和回滚域，若 Rust 能改善所有权表达、锁域边界、失败清理或不变量可读性，可主动使用 Rust；不要求先复现 bug，也不要求编译器证明所有不变量。具体职责仍按实际状态和收益选择实现语言。简单 dispatch、glue、byte-copy、成熟热点原语及硬件机制可按实际收益保留在 C。经过验证的算法、硬件知识、外部兼容行为和测试资产继续保留。

本计划统一 1.0 的支持范围、完成定义与发布条件；当前实现事实仍以源码和对应运行证据为准。
子系统设计页中“下一阶段”“暂不阻塞首个原型”等措辞不自动豁免 1.0 验收。
已明确未立项的研究设想不自动变成发布承诺；已经开展的能力不得因迁移困难悄悄降为演示或移到 1.1。
范围变更需要显式记录原因、影响和项目负责人的决定，不能通过删除 TODO 或缩减测试完成。

## 2. 平台范围

| 架构 | 1.0 决策 | 要求 |
| --- | --- | --- |
| RISC-V64、AArch64、x86_64、LoongArch64 | 保留主线 | 各自承担真实运行矩阵；构建通过不等于用户态、SMP、设备或桌面通过 |
| RISC-V32、ARM32、ARMv7-M | 保留各自已开展的 32 位/NOMMU/MCU 范围 | 不因实现路线调整取消；从核心设计阶段约束指针宽度、原子操作、Flash/RAM/栈预算；不要求 MCU 具备完整 hosted 功能 |
| LoongArch32、PPC64LE | 退出 1.0 支持范围 | 无明确用户、维护者或不可替代研究价值；现有实现与历史证据保留用于追溯 |

退出范围是已作出的产品决策。活跃 Make、CI、实例、工具链和测试矩阵已撤下这两个目标，
Makefile 与 `tools/a20` 会拒绝新的活跃构建请求；PPC64LE 实例快照已移到
已退役平台的实例清单与文档。源代码、历史门禁记录和
平台说明继续保留。需要重现历史行为时，使用干净的 `v0.18` checkout；该清理不影响
LoongArch64、RISC-V32、ARM32 或其他共享代码。

板级矩阵在上述架构内逐项列出：ISA、板型、ABI、MMU/NOMMU、CPU 数、设备、部署方式、
工作负载、验收硬件。现有已开展的板级工作仍须收口。只有原本不适用的能力可列 N/A 并说明
硬件原因；缺工具链、无板或暂时跑不过应列为待验证/失败，不能计为 PASS 或自动取消支持。

### 2.1 明确不在 1.0 范围的服务器生产项

[服务器就绪度评估](../status/current/server-readiness.md) §八 的 P1–P3 尾部列出了八项
生产服务器能力。**本轮明确决定它们不属于 1.0 承诺**，因此不再作为缺口留在
[1.0 缺口台账](../status/gaps/README.md)：

| 项 | 归属 |
| --- | --- |
| kdump 执行后端、panic 改为重启 | 1.0 之后 |
| 硬件 watchdog、A/B 分区、dm-verity | 1.0 之后 |
| 硬件 PMU、ftrace/tracepoints | 1.0 之后 |
| virtio-fs / DAX | 1.0 之后 |
| 真 RTC、paravirt clock | 1.0 之后 |
| NUMA、热管理、C-states | 1.0 之后 |

理由有三条，缺一不可：

1. 它们不出现在本文 §3 任何 V1 工作包的完成条件里，也没有被 1.0 平台范围（§2）引用；
   服务器就绪度评估是**生产运维**视角的排序，不是子系统完成清单。
2. 八项在树上都没有已开展的实现：`git grep` 在 `kernel/`、`tools/` 下对 kdump、
   dm-verity、virtio-fs、ftrace、paravirt、C-states 零命中；`NUMA`、`tracepoint`
   的命中全部是 Linux ABI 兼容桩（`sys_mempolicy.c`、`sys_perf.c`），不是实现。
   因此把它们移出 1.0 不违反「已经开展的能力不得悄悄降为演示或移到 1.1」。
3. 其中任何一项如果被某个**保留平台**的板级验收真正需要（例如某块板的时间源），
   它是那块板的平台行内容，归 V1-DRIVER 的平台矩阵，不由本文整体纳入。

这条决定不缩小 §3 任何工作包：V1-DRIVER 的「崩溃恢复」指驱动/设备在途请求的恢复，
不是 kdump；V1-FS 的持久化指已开展后端的 journal/恢复，不含 dm-verity 与 A/B 分区；
V1-CORE 的故障注入指任务/锁契约的失败路径，不是 panic 后自动重启。

### 2.2 明确不在 1.0 范围的 hypervisor 后端

**本轮明确决定：AArch64 EL2、Intel VMX、AMD SVM、A20 `/dev/kvm`、用户态设备模型与
完整 Linux guest 不属于 1.0 承诺。** V1-HYP 的 1.0 范围是既有 RISC-V H 后端的生命周期
（多 VM/多 vCPU 的创建、停止、资源回收与故障回滚）、A20OS RAMFS guest、寄存器级
UART/CLINT 模型，以及 Native 与 Linux 包装共享的 VM 核心（Linux 包装不是 KVM ABI）。

理由：

1. 树上只有 aarch64/x86_64/arm32/loongarch64/ppc64le 的 `hyp_arch.c` 桩，
   `hyp_supported()` 返回 0；没有 EL2/VMX/SVM 的进入/退出、stage-2、设备或中断实现，
   也没有可用的 nested 硬件/固件 runner。把它们留在 1.0 会让 V1-HYP 无法关闭。
2. A20 `/dev/kvm` 需要 fd/ioctl/mmap run page、exit/completion 语义和固定 QEMU 版本
   验收，是独立的 ABI 项目；现有 Linux ABI 的 `hyp_*` syscall 不是 KVM。
3. 用户态设备模型与完整 Linux guest 需要 virtio-blk/net 和 Linux 启动链；树上只有
   轮询 UART/CLINT 的寄存器级模型，属于后续平台项目。
4. HYP-01/02 的验收对象是既有 RISC-V H 后端。把未实现的后端继续挂在 1.0 上，等于用
   范围声明替代运行证据。

影响：§3 的 V1-HYP 行按此收窄；[平台设计](../hypervisor/04-platform-design.md) 的长期
目标结构与多后端路线保留，但不再作为 1.0 完成条件。架构桩、设计文档和历史记录不删除。

## 4. 实现选择与接口冻结

对大量共享状态、争用、复杂引用生命周期、取消和回滚域，若 Rust 能改善所有权表达、锁域
边界、失败清理或不变量可读性，可主动使用 Rust；不要求先复现 bug，也不要求编译器证明
所有不变量。具体职责仍按实际状态和收益选择实现语言。`unsafe`、汇编和 FFI 需说明别名、
生命周期、IRQ/抢占、锁序与硬件前提；Rust 类型不能代替远端代次、缓存一致性或硬件仲裁。

跨语言接口明确借用、持有和消耗，禁止 C/Rust 两侧都认为自己拥有最后一次释放。成熟 C
依赖、汇编、简单 dispatch、glue、byte-copy、热点原语及硬件机制可按收益保留；不以 Rust
比例或删 C 行数定义完成，也不把裸绑定包装成 safe 后宣称内存安全。实现选择应便于审阅，
注释说明关键状态转移和必要 unsafe 前提。

验收顺序：范围与语义草案 → 受影响功能与失败路径验证 → 适用热点性能测量 → 外部 v1 契约。只有比较能澄清行为或性能变化时才做 C/Rust 对照；不要求恢复已退役的 C 实现。
外部契约包括 Native UAPI、Linux 兼容行为、服务/集群线格式、持久化格式及承诺独立发布的
驱动接口。稳定 Rust 内部结构体或函数 ABI 不在承诺内。线格式明确宽度、对齐、字节序、
长度/版本、未知位处理；IDL 生成 C/Rust 绑定并验证布局，不把 Rust 默认布局用于外部 ABI。

冻结前允许修正设计，但每项行为变化登记旧行为、目标契约、迁移方式和新旧验收。
Linux 已有外部语义仍需遵守；Native 有意的不兼容修改须显式版本化、同步 SDK 与调用者。
不能借“尚未冻结”隐藏功能减少，也不能为追求逐字节相同而保留已确认的旧缺陷。

维护的“暂缓”列表。详细条目仍有未核清项时不得宣布清单完整或开始发布冻结。
