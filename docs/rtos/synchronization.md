# 同步机制与优先级继承

本文档说明 CMSIS-RTOS2 同步对象在 Native/MCU 后端上的实现机制与调度协同语义，重点阐述互斥量优先级继承（Priority Inheritance, PI）状态机与 `osKernelLock` 的交互规则。

## 1. 同步对象实现矩阵

| 对象类型 | 内核/人格层分工 | 关键语义与状态保护 |
|---|---|---|
| **互斥量 (Mutex)** | 人格层维护 `owner`、递归计数与等待链；内核执行 PI 调度重排 | 默认启用递归与优先级继承（`osMutexRecursive \| osMutexPrioInherit`）；支持超时与删除保护 |
| **信号量 (Semaphore)** | 人格层维护计数器与上限；通过 futex park 挂起等待者 | 计数型与二值信号量；支持定时获取与动态 release |
| **事件标志 (Event Flags)** | 人格层维护 32 位掩码字与匹配条件；底层复用 futex 字 | 支持 `osFlagsWaitAny`、`osFlagsWaitAll` 与 `osFlagsNoClear` |
| **消息队列 (Message Queue)** | 人格层维护定长消息数组与每消息优先级；futex 实现满/空等待 | `msg_prio` 数值大者先出，同优先级保持 FIFO；插入/取出为 O(n) 滑动，适合小型队列 |
| **内存池 (Memory Pool)** | 人格层维护单链表 free-list 与块越界标志 | 固定块阻塞分配；包含双重释放（double-free）检测 |
| **线程标志 (Thread Flags)** | 绑定至线程控制块的 32 位独立标志字 | 支持线程间单向事件通知与带超时等待 |

所有同步等待均由底层通用阻塞原语 `os_bq`（futex 序列字 + 原子互斥锁）承载，同步对象自身状态由同一把 bq 互斥锁保护，不依赖特权级内部复杂对象表。

## 2. 互斥量与优先级继承机制

### 等待图与人格层链式追溯

当线程请求已被持有的互斥量并发生阻塞时，人格层在挂起前记录依赖关系：

```c
self->wait_owner = m->owner;   /* 记录当前线程直接依赖的目标所有者 */
```

随后沿 `wait_owner` 指针向前回溯依赖链（例如：高优先级任务 A 等待中优先级任务 B 持有的 M2，而 B 又在等待低优先级任务 C 持有的 M1）：

```text
A (High) ──等待 M2──> B (BelowNormal) ──等待 M1──> C (Low)
```

人格层对回溯过程执行严密的边界控制：
- **最大追溯深度限制（8 级）**：防止深层递归导致挂起时延不可预测；当调用深度达到 8 级或检测到自环时，人格层安全终止回溯并终止后续捐赠，避免陷入死锁循环。
- **动态有效优先级传递**：每一跳调用 `task_set_sched(DONATE, priority = 0)`。其中 `priority = 0` 是 Native ABI 约定的特殊原语，指示内核直接读取并捐赠“调用者当前的有效 RT 优先级”，从而保证 A 的高优先级沿链完整下发至 B 与 C。

### 内核优先级捐赠与基准快照

内核中的 `proc_sched_rt_donate(t, priority)` 实现了对目标任务调度的原子提升：

1. **首次捐赠基准快照**：当目标任务首次被提升时（`!t->pi_boosted`），内核通过 `proc_sched_get()` 捕获其原始基准配置（`policy`、`priority`、`nice` 及 `reset_on_fork`），作为后续恢复点。
2. **状态感知就绪重排**：若目标任务处于 `PROC_READY` 状态，内核通过 `proc_sched_set()` 将其从原有优先级队列分桶摘除，插入新的高优先级分桶；若任务处于 `PROC_RUNNING`，则其在下次安全点抢占比较中直接以新优先级参与仲裁；若处于挂起阻塞态，则唤醒入队时直接使用提升后的优先级。
3. **阶梯合并**：若后续收到更高级别的捐赠请求，内核更新当前生效的最大捐赠值；若捐赠值低于当前有效优先级，则直接忽略。多个等待者并发捐赠时，内核只保留一个基准快照和最大有效优先级，较低捐赠不会覆盖较高值；这一点由 SMP2 的 `NATIVE_SMP_PI` 用两个不同优先级的捐赠者各并发捐赠 64 次验证。人格层依靠 `held_mutexes` 计数，只有所有者释放最后一个互斥量时才发送一次 `UNDONATE`，因此内核不需要为每个捐赠者维护独立栈。

### 快照恢复与所有权生命周期

优先级继承提升的生命周期与互斥量所有权严格绑定：

1. **多互斥量计数（`held_mutexes`）**：一个任务可能同时持有多个互斥量。人格层记录每个线程当前持有的互斥量总数。
2. **延迟恢复点**：只有当所有者释放其所持有的**最后一个**互斥量时，人格层才发起 `task_set_sched(UNDONATE)` 调用。
3. **内核基准回退**：内核 `proc_sched_rt_restore()` 在收到还原指令后，恢复首次捐赠时快照记录的基准策略与优先级，并重新分桶就绪队列。这保证了在持有多个互斥量期间，任务不会因释放其中一个锁而过早丧失继承来的优先级。

## 3. 广播唤醒模型与调度裁决

互斥量与信号量在资源可用时使用广播唤醒（`osb_bq_wake_all`）：

```text
释放互斥量/信号量
   │
   ▼
osb_bq_wake_all() 唤醒所有等待该对象的线程
   │
   ▼
所有被唤醒线程同时进入内核 RT 就绪队列
   │
   ▼
内核调度器选择最高优先级任务首先分发运行
   │
   ├─► 最高优先级任务成功获取对象，离开等待
   └─► 其余低优先级任务重新进入 bq 等待队列挂起
```

**设计权衡**：
- **收益**：避免了在内核中为每个 futex 地址维护复杂的优先级红黑树或排序链表，保持内核阻塞路径的极简与高效。
- **代价**：当竞争同一资源的等待线程极多时，会引发一次有限的就绪唤醒与重新入睡；但在典型 MCU 控制系统（等待同一资源的线程通常少于 3 个）中，该开销完全可控。

## 4. 调度器锁与阻塞语义

`osKernelLock()` 映射为任务结构中的计数器 `sched_lock_depth`，其执行语义与普通互斥锁截然不同：

- **推迟抢占**：仅在系统调用返回安全点与中断返回安全点推迟任务切换，确保短小临界区不被其他线程打断。
- **不屏蔽中断**：外部硬件中断（Timer、UART 等）在锁内仍正常响应并执行边沿处理。
- **严禁锁内主动阻塞**：在持锁状态下调用 `osDelay`、`osSemaphoreAcquire` 等会引发任务挂起的接口属于严重编程错误。虽然任务会如期让出 CPU 并保留锁深度，但这彻底违背了锁推迟调度的初衷。对于保护共享数据结构，应严格使用 `osMutex`。

## 5. 异常边界与已知约束

1. **主线程初始化自句柄**：初始 flat program 线程没有显式的父创建者。在 `osKernelInitialize()` 执行期间，系统通过 `task_self` 系统调用为其在句柄表中建立引用，确保主线程可作为其他线程 PI 捐赠的目标。
2. **捐赠执行期间禁止修改基准优先级**：当任务正处于 PI 提升状态时，调用 `osThreadSetPriority` 将被内核拒绝（返回 `osError`），防止覆盖已保存的恢复快照。
3. **超时后的状态一致性**：若等待者因超时提前退出，其 `wait_owner` 关系立即解除；所有者继承的优先级将持续保持，直到其释放持有的最后一个互斥量（保守保留，避免引入复杂动态降级回退导致的优先级反转）。
4. **多核 SMP 约束**：依赖链追踪与 CMSIS 调度器锁深度基于单核单 runqueue 模型；AArch64 SMP2 已验证 RT runqueue 迁移/IPI/`SCHED_DEADLINE`，但跨核 RT PI 与全局调度器锁语义仍未验证。
5. **挂起与同步对象**：`osThreadSuspend()` 对正在等待的目标只设置 pending；其等待完成时唤醒路径发布 STOPPED，`osThreadResume()` 再入 RT 队列。挂起不会取消底层的 futex/对象等待语义。
