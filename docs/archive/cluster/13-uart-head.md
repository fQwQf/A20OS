# UART 主机头节点与混合调用

## 1. 配置和生命周期

当前提供真实 PC 16550 COM2 绑定，端口 0x2f8、115200 8N1、短地址 1：

```sh
make ARCH=x86_64 CLUSTER_UART_COM2=1 dev-build
```

COM1 继续作为控制台；启用选项进入独立 `-clcom2` 构建目录。没有 COM2 的机器会在路由安装时返回错误，不盲目对未知串口发协议。端口的 scratch 寄存器探测、原始 RX/TX 由 `kernel/arch/x86_64/platform/cluster_uart.c` 提供，共用 UART 协议代码不访问硬件。其他主机板可以实现同一字节驱动 seam。

用户态先设置持久 node_id，再安装 leaf 路由；clusterd 可直接完成：

```text
/bin/clusterd-x86_64 <本机32位十六进制ID> <leaf32位十六进制ID> uart:1
```

首次 UART 路由安装在发布路由之前初始化 COM2 并注册链路。注册配置使用内核当前的 node_id、caps 和统一 boot epoch；不会另外生成一个与固定目录不一致的 UART epoch。串口握手仍在独立协议泵异步完成，连接在握手完成前可以返回不可达，客户端在自己的期限内重试。只配置一个 COM2 点对点 leaf；其他短地址被明确拒绝。

头节点与 leaf 的身份必须精确匹配。UART 不能把连接到短地址 1 的任意设备当作已配置的 node_id；会话查询核对完整 128 位身份，调用也受来源/会话校验。 CRC 和物理连线不提供密码学认证，仍遵循统一设计的受控链路部署边界。

## 2. I/O 预算与故障

COM2 由共用的单一 UART polling owner 访问，不与控制台或第二个 IRQ 消费者共享字节流。1024 B 接收环在 TX 等待时也持续排空硬件 FIFO，防止全双工时只发送不接收。TX 每字节等待有次数上限，失败结束当前帧；RX 硬件错误和环满计入 `arch_cluster_uart_com2_drops()`，损坏帧由 SLIP/CRC 丢弃，可靠事务恢复。

该 polling 驱动不能保证任意调度停顿期间无字节丢失。物理吞吐、串口线缆、 CPU 占用和调度抖动须实测，后续 IRQ/DMA 驱动仍须遵守同一单写入者契约。路由删除取消代理，但 COM2 链路保留供重新配置；不改变本机 boot epoch。 leaf 重启经双向 challenge 确认，DOWN 取消旧代理，重新连接取得新 epoch。

## 3. 端到端检查

```sh
make check-cluster-uart
# 有限的连续调用测试，结束后检查代理、在途缓冲和内核任务回收：
python3 tools/check-cluster-uart.py --soak-calls 10000 --timeout 240
```

检查器构建并运行一个完整 x86 内核、Native 程序和独立 leaf 进程。QEMU emulated COM2 使用真实内核寄存器驱动；独立进程直接编译生产 MCU leaf，仅替换板级 byte I/O 与时钟。测试经 Native ABI 完成以下路径：

- 固定目录找到 leaf 的 `work` 槽位和 epoch。
- 默认 96 个、连续负载配置 10000 个 DOT 调用，并实际丢弃一个请求及一个执行后的回复。
- 比较 leaf 算子实际执行次数与不同事务键的数量，验证回复丢失不会重复执行。
- 检查代理/在途字节归零，`/proc/a20/task_lifetime` 的任务对象与僵尸数回到调用前基线，生命周期错误计数不增长。
- 运行 Native agent 与 clusterd，any 解析同时选到主机和 leaf。
- 同一共享图调度器完成 7 任务二叉树，实际目标同时包含主机和 UART leaf。

日志和结构化证据写入 `.kernel-build/cluster/uart/`，包括注入数量、真实执行计数、资源峰值、源码 SHA256、QEMU/主机环境和客户观察到的延迟。一次记录为 96 次顺序 DOT 用时 1830 ms、中位 11 ms、p95 13 ms，包含故障恢复；这是 TCG 与主机 leaf 的单次观察，不是物理 STM32 性能或生产容量指标。重跑保留各次证据再比较，不能把不同源码版本的数据混合成同一结果。

测试不包含物理 Flash 写入和线缆 UART。物理 MCU 身份、固件和接线见[12-mcu-identity.md](12-mcu-identity.md)；跨 UDP→UART 的间接目标会话发现仍是未完成项，不能把当前直连混合树称为完整多跳网关支持。

## 4. 持续负载修复与回归依据

连续负载曾暴露两个独立问题。主叶的 poll 在接收前取时间，收到 PING/HELLO 时又取得稍晚的时间；处理结束后用旧时间减新心跳时间会无符号下溢，导致健康会话被误判超时。主叶现在在 RX 完成后重新采样时钟。配对单测在字节回调中主动推进时钟，分别覆盖主机状态年龄和 leaf watchdog；恢复旧代码时这两个断言分别失败，不能靠短时间运行掩盖边界。

第二个问题来自内部工作线程继承 Native 调用者为父进程。退出的工作线程因此等待用户进程 task_wait，持续新建连接最终耗尽任务/内核栈内存。新增`proc_alloc_detached()` 为内部线程提供没有用户父进程、描述符和信号状态的创建路径；退出后由调度器回收。普通用户子进程仍按原有 wait 语义回收。集群 RX/轮询/维护与连接/导出工作线程均使用此路径。

长负载门禁同时观测任务对象、僵尸与生命周期错误，避免只看到代理表清空就误认为资源全部释放。资源快照的缓冲字节统计口径见 [09-work-agent.md](09-work-agent.md)。

修复后的 10000 次顺序调用门禁通过：DOT 耗时 136258 ms，中位 13 ms、p95 17 ms；任务对象调用前后均为 9，结束僵尸数 0，生命周期错误 0，代理/在途字节为零。 leaf 记录 10001 次 DOT 执行，对应 10001 个不同事务（包含后续混合树的 DOT），有意丢弃的执行后回复没有重复执行。结构化证据保存在`.kernel-build/cluster/evidence/com2-10000/`。这些数值仅属于该次 TCG 运行。
