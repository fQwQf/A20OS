# 协商分片与有界重组

## 1. 能力与消息上限

统一协议保持 32 B CL 帧头和 v0 金样不变。HELLO 的 caps 新增 bit3 `FRAGMENT=8`，表示 v1 可靠 CALL/CALL_REPLY 分片能力。它是传输特性，不属于 Native `cluster_set_self` 的应用角色位；该 syscall 的位掩码仍是 7。 HELLO 必须同时提供 RELIABLE、proto_max≥1、资源档≥2，才能声明 FRAGMENT。旧节点没有此能力时，超出单帧预算的调用仍明确结束；不能静默开始分片。

当前 UDP 主机实现该特性；UART 和 MCU leaf 不启用分片，也不为重组预留 RAM。发送端按双方资源档的较小上限决定逻辑消息预算：

| 资源档 | 逻辑帧缓冲上限 | 最大可靠请求业务字节 | 最大可靠回复业务字节 | 重组上下文 | 重组字节上限 |
|---|---:|---:|---:|---:|---:|
| MCU | 使用单帧 MTU | 使用单帧 MTU−50 | 使用单帧 MTU−54 | 0 | 0 |
| 默认 | 4096 | 4046 | 4042 | 8 | 256 KiB |
| 服务器 | 65590 | 65536 | 65536 | 64 | 4 MiB |

逻辑帧缓冲包含头、会话/回复状态和 CRC，并非业务大小。默认档到服务器档的连接按默认档预算工作，不能依据本机较大的 RAM 向对方发送超限消息。这不扩大服务本身的能力：CW 算子/进程入口仍须服从各自发布的输入输出上限。回复缓存先预留协商的最大回复缓冲，再把完整请求交给服务执行。

服务器的完整 64 KiB 业务负载加前缀会超过 u16。内核的头部视图使用 u32 逻辑长度，拥有者的 retry/replay 缓冲由独立 logical codec 表示；只有这种内部缓冲允许饱和长度字段，线上解码器不接受该表示。传输前必须拆成实际单片，每片的 u16 长度、CRC 与 MTU 均正常。该内部表示不是另一种线上协议。

## 2. 线上分片格式

每片的普通 CL 头为 ver=1、RELIABLE|FRAGMENTED、CALL 或 CALL_REPLY，`seq=txid`，txid 非保留值，CRC16 必须存在。`frag` 低 12 位为从 0 开始的片序号，bit15 仅在最后一片置位，bit12–14 为零。片数最多 64。片后负载为：

| 片内偏移 | 长度 | 内容 |
|---|---:|---|
| 0 | 8 | 来源 boot epoch |
| 8 | 8 | 目的 boot epoch |
| 16 | 4 | 完整逻辑负载字节数，包含一次 16 B 会话前缀 |
| 20 | 4 | 本片业务体偏移，不包含会话前缀 |
| 24 | 可变 | 完整逻辑负载去掉会话前缀后的一个连续区间 |

物理 MTU 决定固定块大小：`MTU−32−2−24`，UDP 1472 B 时为 1414 B。偏移必须等于 `片序号×块大小`；除尾片外长度必须完整，尾标记、总长、片数必须精确一致。回复状态码属于业务体的开头 4 B，重组后按原可靠回复处理。一帧可容纳的消息不能伪装成分片消息；slot-zero 回复收据也不能被分片。

## 3. 接收生命周期与内存纪律

只有已经绑定当前会话的来源才能申请重组资源；先检查长度、会话、类型、片数和偏移，再分配内存。重组由单一 RX owner 修改，资源统计通过核心锁读取；分配和传输 I/O 在锁外。键包含来源/目的、双方 epoch、类型、txid 和 seq。单向 SEND 的 txid 为零，因此不能省略 seq。同一键的槽位、总长或内容冲突会释放缓冲并把上下文标为 poisoned，保留到原超时点；后续片不能利用冲突不断重建内存。

收到相同内容的重复片仅设置既有位，不重复复制或执行。乱序片按位图累计，只有完整覆盖且所有检查通过，才交给原可靠准入、去重和服务分发。缺片不发执行准入 ACK，也不执行部分业务。发送方的原事务重试重新发送全部片；完整请求/回复的至多一次窗口与收据回收机制保持相同语义。

上下文从首片起最多保留 30000 ms，与完整调用期限一致；重复片不刷新期限。原 2000 ms 在持续 10% 丢帧的大消息测试中会早于后续重试清空已有片，因此已调整。槽位和字节上限没有放宽。当前来源/会话校验仍在分配之前。已接纳请求的分片直接触发缓存重放，每事务至多每 250 ms 一次，不为每片另建上下文或放大回复；已经退休/过旧请求丢弃。没有对应在途代理的回复片在分配前拒绝，代理取消后空闲 RX 泵清理其部分回复；有效退休收据立即清理同一事务的部分请求。这些提前清理不依赖延长后的 30 秒上限。队列或字节额度不足时丢弃片，原调用仍受有界重试/最终期限约束。完整负载交接后从重组表摘除，分发结束由 RX owner 释放；统计中的 bytes 不含交接期间的临时负载、分配器开销、网络栈缓冲和物理驱动环。

发送最多连续提交 4 片，然后让出至少一个 1 ms 调度间隔，再继续。此预算用于给本机网络泵和对端有界数据报队列进展机会；不代替拥塞控制，也不承诺任意网络下无丢片。可靠重试仍是恢复机制。

## 4. 可观测性和检查命令

Native `cluster_snapshot(kind=4)` 使用既有 192 B envelope；SDK 提供`a20_cluster_reassembly_resources`，index/generation/reserved 必须为零。 20 个 u64 中索引 0–8 分别为采样毫秒、上下文数、保留字节、字节峰值、最大上下文数、最大字节数、完成数、拒绝片数、超时上下文数，其余为零。 poisoned 上下文计入数量，但不持有负载字节。MCU 档返回零容量，不虚构重组能力。

```sh
make check-cluster-unit
make check-cluster-fuzz
python3 tools/check-cluster-udp.py --faults --restart
python3 tools/check-cluster-udp.py --profile 3 --faults --restart
python3 tools/check-cluster-udp.py --profile 3 --peer-profile 2 --faults --restart
make smoke-native-cluster
```

主机单测直接执行生产 validator/assembler/RX owner：覆盖全部 64118 个多帧长度、尾片先到、重复/冲突、槽位满、首片超时、旧会话、OOM 和资源释放；另有 10 万次精确分配的畸形片测试。ASan/UBSan 运行这些路径，并保留原有 100 万次帧/固件变异与 v0 金样对拍。Native smoke 覆盖新增资源查询的真实 syscall。

双内核检查器在 Ethernet 数据报上丢请求片、丢回复片、延迟片和重复片，检查双方 8 个大消息回显和服务实际执行数。服务器档包含 65534、65535、 65536 B 业务消息；混合资源档检查较小预算。双方完成确认后才检查重组资源回收，避免把另一侧仍在传输的上下文误判为泄漏。这些都是主机/QEMU 证据，不能当作物理板或生产吞吐结论。

跨不同 MTU 的网关当前不会重分片，只能转发能容纳的原片。[15-routed-sessions.md](15-routed-sessions.md) 实现间接会话与路径 MTU 探测；[19-routed-fragmentation.md](19-routed-fragmentation.md) 实现完整 UDP 路径的端到端分片协商。经过 UART 或不能分片的邻接仍使用最小路径单帧预算。

## 5. 本轮实际证据与底层修复

默认、服务器与服务器/默认混合配置的两套独立内核故障检查均通过，日志分别位于 `.kernel-build/cluster/fragment-default-final/`、`fragment-server-heap/`、`fragment-mixed/`。每次目录包含源码 SHA256、资源档、平台/QEMU 版本、故障注入数和有限线上帧记录。服务器档双方确实回显 65536 B，而不是把包含前缀的帧大小误称为 64 KiB 业务消息。服务器与混合档的双方 lwIP 堆用量在大消息前后均为 736 B，结束重组表为 0 个/0 B；这些数值是单次运行观测。

持续双向大消息还揭示了既有 socket 适配层的发送缓冲泄漏。仓库内`udp_sendto_if_src()` 明确保留调用者 pbuf，RAW 发送也保留它；适配层曾错误认为发送 API 已释放，导致 512 KiB 网络堆在连续分片后耗尽，后续心跳和接收停止。UDP/RAW 现在在发送返回后释放自身引用，包括发送错误路径；ARP/输出持有的引用仍由对应所有者释放。修复独立提交为 `76f08e58`，网络套件与 lwIP socket 选项回归通过。大消息门禁检查实际网络堆占用，防止只检查集群表而遗漏网络栈所有权。

夹具先用一个可靠回显确认双方均已完成 HELLO，再执行非可靠 v0 回显检查。否则一侧刚完成自己的 challenge 时，另一侧仍可能等待确认；非可靠调用没有重试，不能用这种启动时差判断稳定数据面的正确性。
