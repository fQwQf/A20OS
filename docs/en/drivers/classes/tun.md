# TUN: Linux ABI and Replaceable Protocol Backends

TUN is a kernel service created by `open("/dev/net/tun")` and `TUNSETIFF`, with no detectable hardware. The `drivers/net/tun.c` module handles names, file ABIs, waiting and bounded message queues; protocol interfaces, routing, IP input, and protocol buffering are managed by the current backend. The common header `net/tun.h` does not include netif/pbuf/mbuf.

## Data and Lifecycle

`net_stack_tun_create` returns an index for the common interface; the driver does not save a pointer to the protocol object. The output callback synchronizes the borrowing of messages, which are returned after copying; it is forbidden to retain the source pointer or to call the protocol backend in reverse from the callback. Synchronized borrowing of input bytes is performed, and the backend calls its own IP input function after completing the copying. The destroy and input/output operations are mutually exclusive; no further callbacks are made to the instance after it returns. Both the physical NIC and TUN go through common filtering/NAT; TUN does not bypass policies.

Control operations are serialized using process context mutexes; callbacks only acquire short-term queue locks. The control mutex can be used to call the backend; backend callbacks cannot acquire this mutex. Interface name queries use an independent table lock and do not enter the backend while holding the table lock. The usercopy function, which may potentially fail, does not hold the protocol execution lock. A failure in the SETIFF copy operation will revoke the interface, allowing the name to be used again; close first stops the backend callback and then clears all queues.

After a persistent interface is closed, the interface is retained, the current queue is released, and it can be re-bound by name; closing a persistent interface destroys it. Control slots and protocol slots are counted separately, and there are still reconnection controls available even after all protocol slots are persisted. `TUNSETPERSIST` uses Linux command 203 with scalar parameters; command 200 (TUNSETNOCSUM) is no longer misused for persistence, nor is TUNGETSNDBUF misused as if it were TUNGETPERSIST.

## Features and Configuration

- Supports L3 TUN for IPv4/IPv6, `IFF_NO_PI`, and PI headers with protocol information.
- MTU/UP/index/name queries are performed through the common interface; the MTU is read directly from the backend without maintaining a secondary cache. MTU queries have no side effects on link state. IPv4 ifreq settings use the correct sockaddr_in address offset.
- The header size of `IFF_VNET_HDR` is 10 bytes; it supports IPv4 checksum completion, TSO4, and USO4. `TUNSETOFFLOAD` only accepts capability bits that are actually implemented; IPv6 GSO is explicitly denied, while standard IPv6 messages are allowed.
- Modifying an interface or making it persistent requires the CAP_NET_ADMIN permission for the network domain it belongs to. Currently, only the initial network domain is supported; TAP, multiple queues, delegated owner/group, and IPv6 GSO are not implemented, so false successes are not returned. The complete interoperability matrix for GSO is not within the scope of normal IP/UDP regression.

`NET_PROFILE_TUN_MAX_DEVS` defines the maximum number of protocol interfaces (default is 2); the number of control slots is twice that value. The number of packets and bytes per interface queue is limited: 2 packets for embedded interfaces, 32 packets for other types, with the byte limit being the depth multiplied by the frame size of that type. Packets exceeding the limit are discarded and counted; unlimited jumbo packets are not retained. The control structure has a compilation assertion of 768 B per slot; resource macros are located in `net/profile.h`. The original budget of 44 KiB did not include the full TUN queue; now, the TUN control and payload items are explicitly accounted for. This item represents the structure/payload budget, and the allocator's rounding and instantaneous packet conversion buffers need to be calculated separately; it should not be considered as a commitment of the entire system's physical memory. The `/proc/net/status` and `/proc/a20/netmem` files report the current slots, queued packets/bytes, discarded packets, static costs, and queue quotas.

## Regression

The file `tools/probes/net-tun-abi-probe.c` is compiled into a single static Linux ELF executable, which runs on both Linux KVM and A20OS. The probe performs the following tasks: IPv4/IPv6 bidirectional UDP communication, 64-round-robin looping, verification of actual cable addresses/ports for IPv6 connected/lazy/unbound-connect states, adjustment of MTU/UP settings, persistent reconnection, reconnection after persisting all protocol settings, 24 cycles of creation/deactivation, and cleanup of EFAULT errors related to read-only ifreq structures. Linux may first send a DAD/RS packet; the probe matches based on the actual UDP content, without assuming that the first packet must contain test data. For IPv6 binding, it waits for the actual DAD response to be received to avoid using the link-local address for cross-segment service detection. The host does not load any additional modules; the test uses a fixed Linux guest with a explicitly installed tun.ko module that matches the kernel version, and its hash is recorded in the manifest.

The original verification logs are located in `build/evidence/net-router-completion-20261029/`. The TUN IPv6 probe also identifies and fixes issues with old UDP sending paths that directly result in rejections for physical domain IPv6 addresses. Delayed binding is now implemented by first binding on the backend before releasing the frontend address/port. This test verifies the specific ABI (Application Binary Interface) behavior but does not indicate that all IPv6 socket options have been fully implemented.

In the original implementation, the packet queuing index started from head=0, and packet dequeuing moved towards tail, potentially leaving empty slots and dangling pointers after the second packet was processed. Now, packets are queued using the formula `(tail + count) % depth`. Both the byte count and the packet count are updated as packets are consumed and returned. 64 packets with unique sequence numbers are used to ensure that repeated looping scenarios are properly handled; the first packet passing through the system cannot be used as a substitute for verifying FIFO behavior.
