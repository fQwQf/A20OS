# 研究问题与动机

> **本文定义论文要解决的问题**。旧版围绕"时态能力/typed channel/混合信任"三条线；重构后收敛为**一条主线 + 三个层面**：问题只有一个——**能力系统从未被采纳，因为它是重写命令；而真实世界的威胁（供应键、插件、包安装）恰恰需要能力纪律**。预算能力（03）、能力信封（05）、单调采用（05 §6）分别是机制、系统贡献、理论三层面的回答。

---

## 1. 核心问题：能力系统的"重写命令"与"授予即永久"

**观察一（重写命令）**：对象能力系统（seL4、Zircon、KeyKOS/EROS、CHERI）提供精确的授权模型，但要求软件**重写**或**从零构建**。seL4 的 5+ 步进程创建、Zircon 的 FIDL 生态——没有现成二进制能跑。因此能力系统四十年来从未被主流采用。

**观察二（授予即永久）**：即使接受重写，权限一旦授予就永久有效，直到显式撤销。能力系统无法表达"这个组件只能在 N 秒内做 M 次 X 类操作"。供应链组件（库/包/插件）共享宿主全部权限，**且权限没有时间边界**。

**观察三（真实世界）**：安全界在凭证层面早已接受临时凭证（OAuth token、JWT、X.509 有效期），但那是**用户态协议**，内核不参与执行；而包安装脚本（npm postinstall、pip build、cargo build）、第三方插件、CI runner——这些**不可信代码以用户全部权限运行**的场景，是 Log4Shell/SolarWinds/XZ 一类的供应链攻击的真实载体。

---

## 2. 三个层面的回答

### 层面 A（机制）：authority 是多维预算

把授权从二元权限推广为**预算向量**（类型 × 权限 × 时间 × 次数 × 传播），单调衰减、不可刷新、过期原子、O(1) 判定。见 **03**。

### 层面 B（系统贡献）：能力信封——给未修改二进制包上能力纪律

**双 ABI 内核是资源获取的唯一咽喉。** 既然所有资源必经 syscall 获取，内核就能在不修改二进制的前提下为每个进程附加能力预算。`envelope_spawn(binary, policy)` 把一个未修改的 Linux 二进制放进"类型 + 权限 + 时间 + 次数 + 传播"的预算信封里。见 **05**。

### 层面 C（理论）：单调采用

能力覆盖率单调增加 ⇒ 保证单调增强、绝不回退。渐进采用无风险。见 **05 §6**。

## 3. 背景接口分析（必要的最小保留）

为支撑上述问题，保留对 POSIX/能力接口的必要批判（详细分析并入 02-system.md）：

- **TOCTOU 根源**：全局字符串/整数标识符的"重新绑定" → handle 的内核管理绑定消除之（旧 01 §2.7 形式化）。
- **fd 无法降权、碎片化标识符、ioctl 逃逸** → 统一 handle + rights + event_wait 的动机。
- **fork 隐式继承全部权限** → spawn 显式注入的最小权限可构造性（06 §2.4 S2）。

**定位**：这些是"为什么要造新 Native ABI"的必要动机，**不是论文贡献**。论文贡献是预算能力 + 信封（03/05）。

---

## 4. 我们刻意不做的事

- 不主张"POSIX 已死"——信封恰恰是"不放弃 Linux 生态"的路线（05）。
- 不主张预算能力解决供应链的一切——只主张攻击面在类型×时间×次数三围收窄（03 定理 7.1）。
- 不声称信封是完整安全沙箱——它附加能力预算，不解决被攻破进程内部行为（ROP 等，见 11）。
- 不做全内核机器验证——只验证能力决策核心（08）。
