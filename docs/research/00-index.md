# A20OS 研究笔记：索引与阅读指南

> **本文是 A20OS 研究的主张、结构与阅读地图**。研究主轴经过两轮收敛：从旧版"5 个候选贡献"→ 第一轮"时态能力为核心"→ 本轮（主会版）重构为**"能力信封"系统贡献 + "预算能力"机制 + "单调采用"理论 + 机器检验核心**。核心洞察：**预算可部署，权限不可部署**。

---

## 1. 一句话论点

> **A20OS 提出"能力信封"：在一个双 ABI 能力内核中，把预算能力（类型 × 权限 × 时间 × 次数 × 传播的内核强制授权，单调衰减、不可刷新、过期原子）以零源码改动的方式施加到未修改的 Linux 二进制上——把能力系统从"重写命令"变成"部署选项"，并在包安装/插件/供应键场景中可证明、可测量地验证。**

### 2.1 Native ABI 在当前范式下的角色（重要）

> **范式转换的后果**：在旧范式（Native ABI 本身是创新）下，Linux ABI 是"生态补充"；在信封范式下，角色对调——**Linux ABI 是被保护的对象，Native ABI 是保护的机制与目的地**。审稿人必然问"Native ABI 有什么用？"——正面回答如下：

| 角色 | 内容 | 为什么非它不可 |
|------|------|--------------|
| **机制基座**（最实在） | 信封的影子 handle、预算字段、sweeper、typed 传播，全部复用 Native 机制（handle_table 时态字段、typed channel） | Linux 无对象能力模型，type/传播维度无法表达——这是"信封不能直接做在 Linux 上"的正面答案 |
| **迁移终点**（叙事） | 单调采用梯子：Linux ABI（无纪律）→ 信封（预算）→ **Native ABI（完整能力）** | 没有目的地，"能力系统的渐进采用"故事不成立，信封退化为"更花哨的沙箱" |
| **架构层**（职责分工） | Native ABI = **可信组件的架构**（显式最小权限、typed IPC、委托）；信封 = **不可信组件的防御**（强制预算） | 防御只约束"扩散"，架构才实现"精确"——两者互补 |

**已识别的弱点与对策**：Native ABI 生态薄弱，审稿人可称其为"没人用的平行 API"。进展：**mksh 已移植到 Native ABI**（`smoke-mlibc-mksh`，内建 + 顺序外部命令经能力安全 `task_clone` 续体 + 检查点 SIGCHLD 完整可用）——证明 Native ABI 不是只能跑 demo。对策：① 论文坚持"Native ABI 非独立贡献，而是基座+目的地"（贡献表已是如此）；② 评估中演示一个**信封做不到、Native 才能做**的场景（如跨信任域多方委托 + typed IPC，见 10 §E6 扩展），让 Native ABI 挣得存在理由。

## 9. 遗留的已知局限

1. **证明未机器检验**：所有证明为纸笔论证；并发精化与内存序依赖 spinlock 原子性假设（08 计划）。
2. **调度公平性假设**：活性性质依赖公平调度（06 §4）。
3. **残余隐信道**：$\mathcal{L}$-noninterference 承认资源/时间/调度信道（06 §8.5.4）。
4. **无硬件 capability**：未探讨 CHERI 结合（09 §2.2 记录为近邻）。
5. **信封调解器未实现**：当前只有 Native 侧预算机制，Linux ABI 进程尚未接入能力纪律。
6. **类型化通道静态分析工具未实现**：推论 2.2.1 只有语义、无分析器（04 §4）。
7. **信封不是完整沙箱**：附加能力预算，不解决被攻破进程内部行为（11 §1）。
8. **Native ABI 管道数据流待解**：mksh 多进程管道（`a | b`）作业等待已不挂起（waitpid 任意子进程扫描 + 检查点 SIGCHLD + native exec 保留 ht），但 dup2+exec 后的管道句柄映射仍有异常；内建与顺序外部命令均正常。`task_clone`（能力安全续体）已实现：无隐式能力继承、COW 内存续体、显式能力清单（`docs/native-abi/08-runtime-status.md §5d`）。
