# A20OS 1.0：子系统稳定性与发布契约

本文定义 A20OS 1.0 阶段的子系统稳定性标准、发布范围与技术契约。系统重点确保内核核心状态机、关键生命周期与并发控制的长期稳定性；各子系统均通过严格的集成测试与工程门禁完成功能闭环与质量验收。简单 dispatch、胶水层（glue）与热点原语保留在 C。

## 1. 交付目标

1.0 版本重点聚焦于核心稳定性：修复已知缺陷、完善核心子系统设计、并在主流支持架构上验证功能与系统鲁棒性。对于包含大量共享状态、锁争用、复杂引用生命周期和资源回收的关键路径，采用更清晰的所有权与边界设计；成熟高效的算法、硬件驱动与外部兼容性资产继续保持稳定。

本规范统一 1.0 的功能支持范围与发布验收条件。架构与驱动设计以代码实现和实际运行测试为最终依据。

## 2. 平台范围

| 架构 | 1.0 决策 | 要求 |
| --- | --- | --- |
| RISC-V64、AArch64、x86_64、LoongArch64 | 保留主线 | 作为首要支持的 64 位计算架构，承担完整的内核、用户态与 SMP 运行验证 |
| RISC-V32、ARM32、ARMv7-M | 保留嵌入式与轻量级支持 | 适用于 32 位、NOMMU 或资源受限 MCU 场景，严格约束内存占用与栈预算 |
| LoongArch32、PPC64LE | 退出 1.0 范围 | 历史实现保留用于技术溯源，当前活跃开发与自动化构建聚焦于主流架构 |

### 2.1 后续版本演进规划（1.0 之后支持）

在系统能力演进路线中，以下企业级生产特性明确规划在 1.0 正式版之后的后续版本中逐步推进：

| 项 | 归属 |
| --- | --- |
| kdump 执行后端、panic 改为重启 | 1.0 之后 |
| 硬件 watchdog、A/B 分区、dm-verity | 1.0 之后 |
| 硬件 PMU、ftrace/tracepoints | 1.0 之后 |
| virtio-fs / DAX | 1.0 之后 |
| 真实 RTC、paravirt clock | 1.0 之后 |
| NUMA、热管理、C-states | 1.0 之后 |

理由有三条：
1. 它们不属于 1.0 核心工作包的交付条件，属于生产运维的高级优化范畴。
2. 避免在核心未冻结前铺开过多边缘功能，集中精力保证基础内核与双 ABI 的绝对稳定。
3. 若某款特定板卡的基础启动确需特定时钟或看门狗，以该板卡的平台驱动为准，不作为全局通用承诺。

这条决定不缩小 §3 任何工作包：V1-DRIVER 的「崩溃恢复」指驱动/设备在途请求的恢复，不是 kdump；V1-FS 的持久化指已开展后端的 journal/恢复，不含 dm-verity 与 A/B 分区； V1-CORE 的故障注入指任务/锁契约的失败路径，不是 panic 后自动重启。

### 2.2 明确不在 1.0 范围的 hypervisor 后端

**明确说明：AArch64 EL2、Intel VMX、AMD SVM、A20 `/dev/kvm`、用户态设备模型与完整 Linux guest 不属于 1.0 承诺。** V1-HYP 的 1.0 范围是既有 RISC-V H 后端的生命周期（多 VM/多 vCPU 的创建、停止、资源回收与故障回滚）、A20OS RAMFS guest、寄存器级 UART/CLINT 模型，以及 Native 与 Linux 包装共享的 VM 核心（Linux 包装不是 KVM ABI）。

理由：

1. AArch64 EL2、ARM32 HYP、RV32 H、Intel VMX 和 AMD SVM 已有基础后端与双 vCPU 小载荷运行记录，见 [多架构后端](../hypervisor/08-multiarch-backends.md)。这些结果不等于完整 OS guest 与长期稳定性验收；新增后端的完整产品化仍独立于 1.0 RISC-V H 生命周期。
2. A20 `/dev/kvm` 需要 fd/ioctl/mmap run page、exit/completion 语义和固定 QEMU 版本验收，是独立的 ABI 项目；现有 Linux ABI 的 `hyp_*` syscall 不是 KVM。
3. 用户态设备模型与完整 Linux guest 需要 virtio-blk/net 和 Linux 启动链；树上只有轮询 UART/CLINT 的寄存器级模型，属于后续平台项目。
4. HYP-01/02 的验收对象是既有 RISC-V H 后端。把未实现的后端继续挂在 1.0 上，等于用范围声明替代运行证据。

影响：§3 的 V1-HYP 行按此收窄；[平台设计](../hypervisor/04-platform-design.md) 的长期目标结构与多后端路线保留，但不再作为 1.0 完成条件。现有后端、设计文档和历史记录继续保留。

### 2.3 发布验收范围裁定

2026-11-14 按项目负责人决定，移除收益或需求尚不明确的统一发布前置要求：ext4 自定义文件数据块校验和、其他 JBD2 日志模式与 fast commit、强制 IRQ 线程化、锁拆分历史 B1 基线和逐锁性能认证，以及所有架构/门禁/syscall 的穷尽覆盖。现有诊断工具、基准和格式拒绝行为继续保留；取消的台账编号不回收。

发布验证按明确的 ISA/板型/ABI/CPU/设备/工作负载支持矩阵执行。正式支持行必须验证承诺的行为，实验行单列限制。ordered 日志的刷盘、revoke 与错误恢复验收已全部完成。多 guest 定时上界与目标应用关键 ABI 边界已完成关闭，重点保障资源生命周期及正式支持配置的关键并发能力。

### 2.4 功能强化移出 1.0

为确保 1.0 版本核心稳定，下列高级功能强化安排到后续版本逐步推进：

- Native 原语上的 Linux 人格层深化及其扩展对照。
- PCI/MSI-X 的跨架构、每 function/queue 亲和性。
- 新增 ACL 权限判定、xattr 命名空间及后端持久化语义。
- 笔记本新增专用外设能力与完整实机认证。
- DRM master/auth、共享访问、多 GPU、BO/GPUVM 与厂商队列等功能深化。

现有基础功能继续保持回归测试；已暴露接口的权限边界、磁盘一致性、内存/DMA 回收及停止失败等正确性缺陷仍按 1.0 契约严格处理。

### 2.5 Native 信号设计边界

在 1.0 版本中，Native 信号统一采用[检查点式通知设计边界](../native-abi/checkpoint-signals.md)。Native 普通通知在运行时明确的检查点处理，内核抢占与强制终止独立执行；Linux ABI 的异步信号兼容范围保持不变。通知、屏蔽、等待唤醒、权限和强制终止的正确性保障继续保持。

### 2.6 ext4 专项任务收敛

针对 ext4 文件系统，1.0 重点收敛并保障标准元数据日志（JBD2）与基础文件操作一致性，已有实现、修复和验证边界保持稳定。

### 2.7 驱动收尾限定为常见 PC 与 QEMU

1.0 版本驱动重点完善已有支持的常见 PC/QEMU 硬件，具体设备与标准见[驱动范围](../drivers/meta/v1-pc-qemu-scope.md)。对既有支持设备的正常使用、错误处理和资源安全提供完整保障。

### 2.8 CI/CD 保持适量

常规 CI 专注于核心保障：代码规范检查、各支持架构内核编译与 QEMU 启动冒烟测试。发布流程负责版本、构建、打包、签名及分发。Native、压力、集群、设备等专项在相关模块改动时按需执行，具体职责见 [CI/CD](../packaging/ci.md)。

## 4. 实现选择与接口冻结

对大量共享状态、争用、复杂引用生命周期、取消和回滚域，若 Rust 能改善所有权表达、锁域边界、失败清理或不变量可读性，可主动使用 Rust；不要求先复现 bug，也不要求编译器证明所有不变量。具体职责仍按实际状态和收益选择实现语言。`unsafe`、汇编和 FFI 需说明别名、生命周期、IRQ/抢占、锁序与硬件前提；Rust 类型不能代替远端代次、缓存一致性或硬件仲裁。

跨语言接口明确借用、持有和消耗，禁止 C/Rust 两侧都认为自己拥有最后一次释放。成熟 C 依赖、汇编、简单 dispatch、glue、byte-copy、热点原语及硬件机制可按收益保留；不以 Rust 比例或删 C 行数定义完成，也不把裸绑定包装成 safe 后宣称内存安全。实现选择应便于审阅，注释说明关键状态转移和必要 unsafe 前提。

验收顺序：范围与语义草案 → 受影响功能与失败路径验证 → 适用热点性能测量 → 外部 v1 契约。只有比较能澄清行为或性能变化时才做 C/Rust 对照；不要求恢复已退役的 C 实现。外部契约包括 Native UAPI、Linux 兼容行为、服务/集群线格式、持久化格式及承诺独立发布的驱动接口。稳定 Rust 内部结构体或函数 ABI 不在承诺内。线格式明确宽度、对齐、字节序、长度/版本、未知位处理；IDL 生成 C/Rust 绑定并验证布局，不把 Rust 默认布局用于外部 ABI。

冻结前允许修正设计，但每项行为变化登记旧行为、目标契约、迁移方式和新旧验收。 Linux 已有外部语义仍需遵守；Native 有意的不兼容修改须显式版本化、同步 SDK 与调用者。不能借“尚未冻结”隐藏功能减少，也不能为追求逐字节相同而保留已确认的旧缺陷。

## 5. TODO 与证据归并

所有活跃工程文档、源码 TODO、已知问题和未完成设计里程碑都要映射到上表 ID，再拆成唯一需求记录。记录至少包括：来源/符号、目标行为、实现状态、负责人、适用矩阵、验收命令、功能用例、性能指标、证据位置、阻塞原因。无负责人的未完成需求仍是阻塞，不可默认为取消。

| 状态 | 关闭规则 |
| --- | --- |
| 待实现 | 补实现并进入功能、失败路径和性能验收 |
| 已实现待验证 | 补真实运行；静态标记、编译和测试代码存在不能替代结果 |
| 历史通过待复验 | 保留原提交/配置，在候选上重新验证；不得把历史 PASS 直接继承 |
| 重复/过时 | 指向合并后的需求或实际实现及证据，保留审计去向 |
| 退出范围 | 仅用于明确决策，例如 LoongArch32/PPC64LE；记录原因和清理工作 |
| 完成 | 实现、所有适用功能验收、性能对照和文档一致性均满足，附候选证据 |

1.0 前必须关闭所有有效交付项。单纯让文本中搜不到 TODO 不是验收；历史档案的原始记录继续保留，研究设想和未立项扩展保持明确标签。新增缺陷或遗漏进入同一清单，不另建无人维护的“暂缓”列表。详细条目仍有未核清项时不得宣布清单完整或开始发布冻结。
