# A20OS 1.0：子系统稳定性与发布契约

本文是 A20OS 1.0 阶段的子系统稳定性与发布验收契约。Rust 迁移覆盖复杂状态、生命周期、回滚与并发职责；各模块的范围与验证证据见 [当前模块状态索引](../status/current/module-status.md)。各子系统需按契约完成功能、失败路径、集成和稳定性验收；简单 dispatch、glue 与热点 C 原语保留在 C。

## 1. 交付目标

1.0 同时完成三件事：修复现有缺陷、完成已经推进开发的子系统、验证功能与稳定性。只让已有 smoke 变绿、只迁移语言、只启动一个演示程序，都不能作为子系统开发完成。对大量共享状态、争用、复杂引用生命周期、取消和回滚域，若 Rust 能改善所有权表达、锁域边界、失败清理或不变量可读性，可主动使用 Rust；不要求先复现 bug，也不要求编译器证明所有不变量。具体职责仍按实际状态和收益选择实现语言。简单 dispatch、glue、byte-copy、成熟热点原语及硬件机制可按实际收益保留在 C。经过验证的算法、硬件知识、外部兼容行为和测试资产继续保留。

本计划统一 1.0 的支持范围、完成定义与发布条件；当前实现事实仍以源码和对应运行证据为准。子系统设计页中“下一阶段”“暂不阻塞首个原型”等措辞不自动豁免 1.0 验收。已明确未立项的研究设想不自动变成发布承诺；已经开展的能力不得因迁移困难悄悄降为演示或移到 1.1。范围变更需要显式记录原因、影响和项目负责人的决定，不能通过删除 TODO 或缩减测试完成。

## 2. 平台范围

| 架构 | 1.0 决策 | 要求 |
| --- | --- | --- |
| RISC-V64、AArch64、x86_64、LoongArch64 | 保留主线 | 按正式支持矩阵承担对应真实运行；构建通过不等于用户态、SMP、设备或桌面通过 |
| RISC-V32、ARM32、ARMv7-M | 保留各自已开展的 32 位/NOMMU/MCU 范围 | 不因实现路线调整取消；从核心设计阶段约束指针宽度、原子操作、Flash/RAM/栈预算；不要求 MCU 具备完整 hosted 功能 |
| LoongArch32、PPC64LE | 退出 1.0 支持范围 | 无明确用户、维护者或不可替代研究价值；现有实现与历史证据保留用于追溯 |

退出范围是已作出的产品决策。活跃 Make、CI、实例、工具链和测试矩阵已撤下这两个目标， Makefile 与 `tools/a20` 会拒绝新的活跃构建请求；PPC64LE 实例快照已移到已退役平台的实例清单与文档。源代码、历史门禁记录和平台说明继续保留。需要重现历史行为时，使用干净的 `v0.18` checkout；该清理不影响 LoongArch64、RISC-V32、ARM32 或其他共享代码。

板级矩阵在上述架构内逐项列出：ISA、板型、ABI、MMU/NOMMU、CPU 数、设备、部署方式、工作负载、验收硬件。每行明确正式支持或实验状态及承诺能力。正式支持行缺工具链、无板或暂时跑不过应列为待验证/失败，不能计为 PASS；实验行不自动形成完整 hosted 功能的发布承诺。支持范围调整应按 §2.3 显式登记。

**板级范围界定**：LicheeRV Nano、Milk-V Duo、Allwinner H616、Rockchip RK3328 四块开发板暂不列入 1.0 运行验收矩阵。原因在于缺乏实体板卡及可用 SD/eMMC 或 GMAC 驱动。这四个目标保留 `check-lao64-board-builds` / `check-arm-board-builds` 的编译验证目标及相关源码文档，后续硬件到位后可重新开展运行验收。

### 2.1 明确不在 1.0 范围的服务器生产项

[服务器就绪度评估](../status/current/server-readiness.md) §八 的 P1–P3 尾部列出了八项生产服务器能力。**已明确裁定它们不属于 1.0 承诺**，因此不再作为缺口留在[1.0 缺口台账](../status/gaps/README.md)：

| 项 | 归属 |
| --- | --- |
| kdump 执行后端、panic 改为重启 | 1.0 之后 |
| 硬件 watchdog、A/B 分区、dm-verity | 1.0 之后 |
| 硬件 PMU、ftrace/tracepoints | 1.0 之后 |
| virtio-fs / DAX | 1.0 之后 |
| 真 RTC、paravirt clock | 1.0 之后 |
| NUMA、热管理、C-states | 1.0 之后 |

理由有三条，缺一不可：

1. 它们不出现在本文 §3 任何 V1 工作包的完成条件里，也没有被 1.0 平台范围（§2）引用；服务器就绪度评估是**生产运维**视角的排序，不是子系统完成清单。
2. 八项在树上都没有已开展的实现：`git grep` 在 `kernel/`、`tools/` 下对 kdump、 dm-verity、virtio-fs、ftrace、paravirt、C-states 零命中；`NUMA`、`tracepoint`的命中全部是 Linux ABI 兼容桩（`sys_mempolicy.c`、`sys_perf.c`），不是实现。因此把它们移出 1.0 不违反「已经开展的能力不得悄悄降为演示或移到 1.1」。
3. 其中任何一项如果被某个**保留平台**的板级验收真正需要（例如某块板的时间源），它是那块板的平台行内容，归 V1-DRIVER 的平台矩阵，不由本文整体纳入。

这条决定不缩小 §3 任何工作包：V1-DRIVER 的「崩溃恢复」指驱动/设备在途请求的恢复，不是 kdump；V1-FS 的持久化指已开展后端的 journal/恢复，不含 dm-verity 与 A/B 分区； V1-CORE 的故障注入指任务/锁契约的失败路径，不是 panic 后自动重启。

### 2.2 明确不在 1.0 范围的 hypervisor 后端

**明确说明：AArch64 EL2、Intel VMX、AMD SVM、A20 `/dev/kvm`、用户态设备模型与完整 Linux guest 不属于 1.0 承诺。** V1-HYP 的 1.0 范围是既有 RISC-V H 后端的生命周期（多 VM/多 vCPU 的创建、停止、资源回收与故障回滚）、A20OS RAMFS guest、寄存器级 UART/CLINT 模型，以及 Native 与 Linux 包装共享的 VM 核心（Linux 包装不是 KVM ABI）。

理由：

1. AArch64 EL2、ARM32 HYP、RV32 H、Intel VMX 和 AMD SVM 已有基础后端与双 vCPU 小载荷运行记录，见 [多架构后端](../hypervisor/08-multiarch-backends.md)。这些结果不等于完整 OS guest 与长期稳定性验收；新增后端的完整产品化仍独立于 1.0 RISC-V H 生命周期。
2. A20 `/dev/kvm` 需要 fd/ioctl/mmap run page、exit/completion 语义和固定 QEMU 版本验收，是独立的 ABI 项目；现有 Linux ABI 的 `hyp_*` syscall 不是 KVM。
3. 用户态设备模型与完整 Linux guest 需要 virtio-blk/net 和 Linux 启动链；树上只有轮询 UART/CLINT 的寄存器级模型，属于后续平台项目。
4. HYP-01/02 的验收对象是既有 RISC-V H 后端。把未实现的后端继续挂在 1.0 上，等于用范围声明替代运行证据。

影响：§3 的 V1-HYP 行按此收窄；[平台设计](../hypervisor/04-platform-design.md) 的长期目标结构与多后端路线保留，但不再作为 1.0 完成条件。现有后端、设计文档和历史记录继续保留。

### 2.3 发布验收范围裁定

2026-11-14 按项目负责人决定，移除收益或需求尚不明确的统一发布前置要求：ext4 自定义文件数据块校验和、其他 JBD2 日志模式与 fast commit、强制 IRQ 线程化、锁拆分历史 B1 基线和逐锁性能认证，以及所有架构/门禁/syscall 的穷尽覆盖。现有诊断工具、基准和格式拒绝行为继续保留；取消的台账编号不回收。

发布验证按明确的 ISA/板型/ABI/CPU/设备/工作负载支持矩阵执行。正式支持行必须验证承诺的行为，实验行单列限制，未验证不计 PASS；不要求架构与全部能力做笛卡尔积。ordered 日志的刷盘、revoke 与错误冷恢复验收已完成，见 [N14 记录](../status/current/fs-status.md#2026-11-16-ordered-日志验收n14)。多 guest 定时上界与目标应用关键 ABI 边界已有关闭记录；仍须完成资源生命周期及正式支持配置的关键并发与候选交付。受影响热点或性能收益声明须有可复现测量。

### 2.4 功能强化移出 1.0

2026-11-16，项目负责人决定将下列功能强化安排到后续版本，并从 1.0 缺口、实施队列与完成条件删除：

- Native 原语上的 Linux 人格层深化及其扩展对照（原 N06）。
- PCI/MSI-X 的跨架构、每 function/queue 亲和性与新增专项认证（原 N10/N11/N12）。
- 新增 ACL 权限判定、xattr 命名空间及后端持久化语义。
- 笔记本新增设备能力与完整实机认证；已有实测结果和限制保留。
- DRM master/auth、共享访问、多 GPU、BO/GPUVM 与厂商队列等功能深化。

后续入口统一为 [功能强化路线](../roadmap/next-horizon.md#后续版本功能强化)。这些事项的状态为“退出 1.0、后续开发或验收”，不计为已经完成。现有正常功能继续回归；已暴露接口的权限边界、磁盘一致性、内存/DMA 回收及停止失败等正确性缺陷仍按 1.0 契约处理。新增功能与新增实机认证不再阻塞发布；QEMU 结果不因此升级为实机认证。

### 2.5 Native 信号设计边界

2026-11-16，按项目负责人决定，删除“完整 Native 异步信号”的 1.0 必须项，统一为[检查点式通知设计边界](../native-abi/checkpoint-signals.md)。Native 普通通知在运行时明确的检查点处理，内核抢占与强制终止独立执行；Linux ABI 的异步信号兼容范围保持不变。通知、屏蔽、等待唤醒、权限和强制终止的已有正确性要求继续保留。此项是设计边界裁定，不标记为异步处理器已完成，也不自动列入下一版本待办。

### 2.6 ext4 专项任务移除

按项目负责人要求，原 N21（ext4 orphan 收尾专项）从 1.0 必须项和剩余任务中删除，不再安排其关键无日志崩溃切点、补偿失败后的完整服务/系统重启隔离，以及分配器、HTree、rename 的专项恢复验收，也不自动转入后续版本待办。已有实现、修复、故障记录和验证边界保留在 [FS 现状](../status/current/fs-status.md)；这是任务范围调整，不增加新的实现或验收完成声明。

### 2.7 驱动收尾限定为常见 PC 与 QEMU

按项目负责人要求，V1-DRIVER 只完善已有支持的常见 PC/QEMU 硬件，具体设备与关闭条件见[驱动范围](../drivers/meta/v1-pc-qemu-scope.md)。Hi3861 等板级外设不再逐项完善，不要求对全部厂商或实板收集停止/失联证据；既有支持设备的正常使用、错误处理和资源安全仍须正确。已完成的板级改进保留，未完成的专项不默认转为后续版本任务。

### 2.8 CI/CD 保持适量

2026-11-17 按项目负责人要求，常规 CI 仅保留基础检查、支持架构内核编译与一次 QEMU 启动。发布只负责版本、构建、打包、签名及分发，不重复整套 CI 或逐镜像启动认证。Native、压力、集群、设备等专项在相关修改时按需运行；原 N02 不再要求完整 Native CI 和发布前置矩阵。候选 `94bbdbb12` 的基础 CI 已通过，记录见[候选状态](../status/current/v1.0-candidate.md)；具体职责见 [CI/CD](../packaging/ci.md)。范围取消不写成历史验收通过。

“完成开发”指已约定范围的正常路径、边界、失败回滚、并发、资源耗尽、恢复、可观测性、用户文档和集成运行均完成。它不要求实现世界上所有同类功能，但不允许以原型已启动代替上述范围。分配失败、跨 CPU 取消、服务/节点重启等场景不得只留代码而没有可执行验收。

## 4. 实现选择与接口冻结

对大量共享状态、争用、复杂引用生命周期、取消和回滚域，若 Rust 能改善所有权表达、锁域边界、失败清理或不变量可读性，可主动使用 Rust；不要求先复现 bug，也不要求编译器证明所有不变量。具体职责仍按实际状态和收益选择实现语言。`unsafe`、汇编和 FFI 需说明别名、生命周期、IRQ/抢占、锁序与硬件前提；Rust 类型不能代替远端代次、缓存一致性或硬件仲裁。

跨语言接口明确借用、持有和消耗，禁止 C/Rust 两侧都认为自己拥有最后一次释放。成熟 C 依赖、汇编、简单 dispatch、glue、byte-copy、热点原语及硬件机制可按收益保留；不以 Rust 比例或删 C 行数定义完成，也不把裸绑定包装成 safe 后宣称内存安全。实现选择应便于审阅，注释说明关键状态转移和必要 unsafe 前提。

验收顺序：范围与语义草案 → 受影响功能与失败路径验证 → 适用热点性能测量 → 外部 v1 契约。只有比较能澄清行为或性能变化时才做 C/Rust 对照；不要求恢复已退役的 C 实现。外部契约包括 Native UAPI、Linux 兼容行为、服务/集群线格式、持久化格式及承诺独立发布的驱动接口。稳定 Rust 内部结构体或函数 ABI 不在承诺内。线格式明确宽度、对齐、字节序、长度/版本、未知位处理；IDL 生成 C/Rust 绑定并验证布局，不把 Rust 默认布局用于外部 ABI。

冻结前允许修正设计，但每项行为变化登记旧行为、目标契约、迁移方式和新旧验收。 Linux 已有外部语义仍需遵守；Native 有意的不兼容修改须显式版本化、同步 SDK 与调用者。不能借“尚未冻结”隐藏功能减少，也不能为追求逐字节相同而保留已确认的旧缺陷。

## 5. TODO 与证据归并

所有活跃工程文档、源码 TODO、已知问题和未完成设计里程碑都要映射到上表 ID，再拆成唯一需求记录。记录至少包括：来源/符号、目标行为、实现状态、负责人、适用矩阵、验收命令、功能用例、性能指标、证据位置、阻塞原因。无负责人的未完成需求仍是阻塞，不可默认为取消。

| 状态 | 关闭规则 |
| --- | --- |
| 待实现 | 补实现并进入功能、失败路径和性能验收 |
| 已实现待验证 | 补真实运行；静态标记、编译和测试代码存在不能替代结果 |
| 历史通过待复验 | 保留原提交/配置，在候选上重新验证；不得把历史 PASS 直接继承 |
| 重复/过时 | 指向合并后的需求或实际实现及证据，保留审计去向 |
| 退出范围 | 仅用于明确决策，例如 LoongArch32/PPC64LE；记录原因和清理工作 |
| 完成 | 实现、所有适用功能验收、性能对照和文档一致性均满足，附候选证据 |

1.0 前必须关闭所有有效交付项。单纯让文本中搜不到 TODO 不是验收；历史档案的原始记录继续保留，研究设想和未立项扩展保持明确标签。新增缺陷或遗漏进入同一清单，不另建无人维护的“暂缓”列表。详细条目仍有未核清项时不得宣布清单完整或开始发布冻结。
