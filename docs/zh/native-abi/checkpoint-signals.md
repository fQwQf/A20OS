# Native 信号与通知的设计边界

2026-11-16 按项目负责人决定，Native 保持检查点式通知模型。“完整 Native 异步信号”不属于 1.0 必须项，也不作为默认延后到下一版本的待办。这是设计边界的统一，不是宣布已经实现任意执行点的异步处理器。

## 投递与执行分工

| 机制 | 执行契约 |
| --- | --- |
| 普通 Native 通知 | 内核记录 pending 状态并通知已接入的事件/等待路径；用户处理器由运行时在明确定义的检查点执行，不在任意用户指令位置插入执行。 |
| 屏蔽与队列 | 保留既有进程级检查点接口及可选线程级 mask/queue 契约。屏蔽、查询、消费与通知的对象作用域按对应 syscall 定义。 |
| 协作取消与退出清理 | 运行时在其取消点决定如何停止工作和清理资源；检查点通知不保证任意时刻立即执行处理器。 |
| 内核抢占与强制终止 | 继续由内核实现，不依赖应用主动到达通知检查点。强制终止不承诺执行用户态处理器或析构清理。 |
| Linux ABI 信号 | 保留其 POSIX/Linux 异步投递、屏蔽和处理器返回契约，按兼容范围修复缺陷。本决定不缩减 Linux ABI 的既有信号语义。 |

检查点由运行时接口明确规定，例如已接入的可中断等待返回或显式检查操作。不能把任意 syscall 返回都自动视作可运行用户处理器的安全点；检查点也不意味着处理器可以无视应用自身的锁和状态约束。

普通通知的响应时间取决于检查点分布。长时间纯计算若需要及时处理可捕获通知，应主动检查或由运行时安排安全点；没有检查点时不承诺用户处理器的延迟上界。内核仍可抢占或强制终止这类任务。

## libc 与应用边界

Native mlibc 可以把部分 POSIX 信号 API 映射到检查点协议，但不因此宣称具备完整 POSIX 异步处理器语义。依赖该语义的现有应用使用 Linux ABI；Native 应用使用其已声明的通知、事件和任务控制接口。

不改变既有 syscall 编号、结构布局、默认进程级接口或已实现的线程级接口。将来若改变默认投递时机，应按 [Native ABI 兼容规则](00-overview.md#兼容策略) 单独设计，不能作为无感升级。

## 1.0 范围与现状

1.0 保留现有通知、屏蔽、等待唤醒、任务权限和强制终止的正确性要求。通知丢失、错误作用域、无法终止任务或资源泄漏属于现有功能缺陷，继续处理；不再新增“实现完整 Native 异步信号”的发布门槛。

现有实现与运行范围见 [Native 运行时现状](../status/current/native-abi-runtime-status.md)，事件接入边界见 [Channel / Event Queue](05-ipc.md)。本次范围决定没有新增实现或运行验证，也不改变尚未关闭的目标应用 ABI 与正式支持配置要求。
