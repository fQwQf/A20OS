# Native 检查点信号与异步通知设计规范

Native ABI 采用**显式检查点通知模型**（Checkpoint-based Notification Model）。与传统 POSIX 异步信号在任意用户指令位置抢占插入处理器的行为不同，Native 原语通过在预定义的安全点（检查点）投递和处理通知，以保障用户态状态更新与锁契约的确定性。

---

## 1. 核心设计原则

在任意执行点插入用户处理器，会导致应用程序在持有自旋锁或执行状态尚未提交时发生重入死锁或状态破坏。Native 机制采用显式检查点，使运行时能够安全安排通知处理与资源清理：
- **安全检查点投递**：需要响应外部事件的计算密集型循环主动设立检查点，换取明确的执行时机与状态一致性。
- **职责严格分离**：内核抢占与强制终止（Force Termination）负责调度抢占与系统安全，不受用户检查点阻塞；Linux ABI 保持其 POSIX 异步信号兼容路径，二者互不干扰。

---

## 2. 机制分工与执行契约

| 机制 | 执行契约 |
| --- | --- |
| **普通 Native 通知** | 内核记录 pending 状态并通知已接入的事件/等待路径；用户处理器由运行时在明确定义的检查点执行，不在任意用户指令位置插入执行。 |
| **屏蔽与队列** | 保留进程级检查点接口及线程级 mask/queue 契约。屏蔽、查询、消费与通知的对象作用域按对应系统调用严格划分。 |
| **协作取消与退出清理** | 运行时在取消点决定如何停止工作和清理资源；检查点通知确保执行流总是在安全状态下释放锁与内存。 |
| **内核抢占与强制终止** | 由内核直接执行，不依赖应用主动到达通知检查点。强制终止时直接回收底层对象资源。 |
| **Linux ABI 信号** | 完整保留 POSIX/Linux 异步投递、屏蔽掩码和 sigreturn 返回契约，按既定兼容范围处理。 |

检查点由运行时接口明确规定（如可中断的系统调用返回、Channel 接收阻塞返回或显式 `event_queue_poll` 轮询点）。

---

## 3. libc 与应用边界

- **Native SDK 与 mlibc**：mlibc 将部分 POSIX 信号 API 映射到检查点协议，适合结构化原生应用。依赖任意指令抢占异步信号的遗留软件则通过 Linux ABI 运行。
- **长时间计算任务**：若需响应优雅取消通知，应在迭代步中主动调用检查点接口或事件队列轮询；内核仍可根据调度策略抢占时间片或执行强制终止。
