# Intel J1900 工控机

提供 BIOS/64 位 UEFI 内核检查实例，以及原生 64 位 UEFI 串口 shell、GOP 显示和 HDA 音频实例。实机运行状态：未验证。 J1900 是处理器型号，不是固定主板：固件位数、串口地址/模式、网卡和存储控制器由具体主板决定。不能由“有 PCI”推导出板载网卡已有驱动。

## 系统支持范围

`instances/j1900-pc.toml` 复用 `BOARD=x86_64-pc`，先单核、embedded 驱动、`BRINGUP=1`。该配置没有 shell，完成内核自检后可能关机，串口日志才是验收依据。

早期 BIOS 与 UEFI 内核入口已改为 2 MiB 页：Intel 64 不保证可选的 1 GiB 页支持，不能因 QEMU 默认 CPU 支持就让真实机器在第一次高半区取指时产生页故障。 4 GiB 以上的 RAM 映射也使用 2 MiB 叶子，W^X 初始化同时支持这种初始页表。 MMIO 页使用默认 PAT 的 UC 编码（PWT|PCD），保留低端 RAM 的 WB 属性。

默认内核从物理 **32 MiB（`0x02000000`）** 加载。内存图中的保留区、ACPI NVS 及实际 ACPI 表不会交给分配器；完整内核与保留区重叠时会停止。如固件占用默认位置，只能在确认另一完整可用区后重建，例如`tools/a20 package j1900-pc -- X86_KERNEL_LOAD_ADDRESS=0x04000000`。参数必须 2 MiB 对齐且位于 `0x00200000..0x3e000000`，完整内核不能越过初始 1 GiB 映射。不同地址使用独立构建目录；复制已有 ELF 到另一地址不能替代重新构建。

## 宿主依赖与打包

以下命令面向 Linux 构建主机。Debian/Ubuntu 安装 x86-64 GNU 工具链和同时支持 BIOS/UEFI 的 GRUB 打包依赖：

```sh
sudo apt-get install build-essential git curl ca-certificates python3 \
  gcc-x86-64-linux-gnu binutils-x86-64-linux-gnu \
  grub-pc-bin grub-efi-amd64-bin xorriso
```

安装 rustup 后配置仓库指定的 Rust 1.96.0；若尚无 rustup，可先执行下面前两条命令。已有 rustup 时可跳过安装器：

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/a20-rustup-init.sh
sh /tmp/a20-rustup-init.sh -y --profile minimal --default-toolchain 1.96.0
. "$HOME/.cargo/env"
rustup toolchain install 1.96.0 --profile minimal
rustup target add --toolchain 1.96.0 x86_64-unknown-none
```

下列仓库命令均在 A20OS 源码根目录执行；首次构建先运行 `git submodule update --init --recursive`。主机 Python 必须为 3.11 或更新版本，可用 `python3 --version` 确认。首次下载源码、Rust 组件和 Cargo 依赖需要联网。

```sh
tools/a20 check j1900-pc
tools/a20 build j1900-pc
tools/a20 package j1900-pc
tools/a20 ledger j1900-pc
```

产物为 `build/x86_64-pc/a20os-rescue.iso`，与通用 `x86_64-pc` 实例共享发布路径；切换实例后应重新打包并保存账本。GRUB 只会加入宿主已安装的固件平台模块：缺 `grub-pc-bin` 就不能承诺 BIOS 启动，缺 EFI 模块也不能承诺 UEFI 启动。可用 `xorriso -indev build/x86_64-pc/a20os-rescue.iso -report_el_torito plain` 核对实际启动目录。`GRUB_RESCUE_DIR` 可显式选择一个 GRUB 平台模块目录用于单一路径验证；通常无需设置。

## 写 U 盘与启动

```sh
lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS
tools/a20 deploy j1900-pc --no-build --no-console \
  --media-device /dev/disk/by-id/usb-实际U盘 --dry-run
```

确认路径，卸载该盘的分区，去掉 `--dry-run` 写入。需要写权限时仅对这一步提权。`/dev/sdX` 是模板，不是实际目的盘；工具不能判断你的购买意图。

在调试主机打开唯一串口会话，再启动工控机：

```sh
tools/a20 console j1900-pc --interactive --serial /dev/serial/by-id/实际串口
```

从固件菜单选择 U 盘；如固件开启 Secure Boot，需要允许当前未签名的启动介质。此路径面向 BIOS 或 64 位 UEFI；32 位 UEFI 并不在当前支持范围。串口应为标准 COM1（I/O `0x3f8`、38400 8N1）。部分工控机可配置 RS-232/422/485，应按主板说明选 RS-232 并用对应 USB-RS232 转接器，不能把 DB9 RS-232 直接接到 TTL 转接器。若 COM 地址、电平或连接器引脚未知，先用原厂系统确认。BIOS 检查实例没有显示交接；原生 UEFI shell 实例可使用固件 GOP 模式。串口日志仍是启动诊断入口。

实例要求看到 multiboot 命令行、usable RAM、`[INIT] System ready (bringup, no userspace)`。不以串口回显 shell 命令作为通过依据。完整日志保存至 `.kernel-build/console/j1900-pc.log`。

## 原生 UEFI shell 与媒体实例

`j1900-pc-uefi-shell` 使用 `BRINGUP=0`、单核、embedded 驱动，内嵌静态`init`、`mksh` 和基本命令，不依赖磁盘用户态。它与前述 GRUB ISO 是独立产物。除上述构建工具外，打包需要 `sudo apt-get install parted mtools`。

```sh
tools/a20 check j1900-pc-uefi-shell
tools/a20 build j1900-pc-uefi-shell
tools/a20 package j1900-pc-uefi-shell
tools/a20 ledger j1900-pc-uefi-shell
```

产物为 `build/x86_64-pc/a20os-j1900-shell-uefi.img`，GPT ESP 内包含`EFI/BOOT/BOOTX64.EFI`，用户态嵌入内核，不需另外制作 FAT 根目录。写盘与串口操作如下；先核对目标 U 盘并卸载其分区，确认 dry-run 输出后去掉`--dry-run` 执行写入：

```sh
lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS
tools/a20 deploy j1900-pc-uefi-shell --no-build --no-console \
  --media-device /dev/disk/by-id/usb-实际U盘 --dry-run
tools/a20 console j1900-pc-uefi-shell --interactive \
  --serial /dev/serial/by-id/实际串口
```

从主板启动菜单选择 64 位 UEFI U 盘入口，按前文 COM1/38400/RS-232 要求接线。验收应看到 `System ready`、init 执行 mksh，并实际运行：

```sh
uname -a
ls /bin
echo serial-shell-ok
sleep 1
ps
videoplay --test 320 240 30
audioplay --tone 1000 --duration 500
```

`videoplay` 使用 UEFI 已设置的 GOP 模式和公共 `simplefb`，支持 RGB/BGR 与有效 BitMask 布局；没有 Intel GPU 模式设置、热插拔或硬件视频解码。 HDA 按实际 codec/DAC/pin 路径探测，支持 PCM 48 kHz、双声道、16 位；主板专用功放控制和 HDMI 音频路径尚未普遍覆盖。没有 GOP 或无法识别音频路径时，串口 shell 仍可用于诊断。未承诺 SSH：需先核对具体板载 PCI 网卡与网络配置。

媒体实例只读挂载首个可用 FAT32 介质（裸 FAT 或 GPT 分区）到 `/media`，保留内嵌 `/bin`。可在宿主将短片转换后放入启动 ESP（先 package，后复制，重新 package 会覆盖）：

```sh
ffmpeg -i input.mp4 -an -vf 'fps=24,scale=320:240,format=rgb24' \
  -c:v rawvideo -f rawvideo clip.rgb
ffmpeg -i input.mp4 -vn -ar 48000 -ac 2 -c:a pcm_s16le clip.wav
mcopy -i build/x86_64-pc/a20os-j1900-shell-uefi.img@@1048576 clip.rgb ::/clip.rgb
mcopy -i build/x86_64-pc/a20os-j1900-shell-uefi.img@@1048576 clip.wav ::/clip.wav
sha256sum build/x86_64-pc/a20os-j1900-shell-uefi.img > build/x86_64-pc/a20os-j1900-shell-uefi.img.sha256
tools/a20 ledger j1900-pc-uefi-shell
```

写入 U 盘启动后，在串口 shell 执行 `videoplay /media/clip.rgb 320 240 24` 和`audioplay /media/clip.wav`。256 MiB 启动盘要为 EFI 内核留空间；RGB24 十秒 24 fps 约 55.3 MB，请先使用短片。支持存储控制器驱动能读取介质才会出现 `/media`；缺少控制器支持时仍可运行测试图和测试音。

媒体播放器目前接受宿主预转换的 RGB24 和 PCM WAV，没有原生 MP4/H.264 解码，也没有音画同步。具体文件准备、介质读取和可重复验证步骤见[固件线性显示与软件视频](../graphics/firmware-video.md)。 OVMF/QEMU 已验证真实 GOP 像素、300 帧用户态呈现、HDA 非零双极 PCM 输出及正常关机；这些结果不能替代 J1900 主板、显示器和 codec 的实机验收。

## 限制

`j1900-pc` 检查实例不提供用户态；`j1900-pc-uefi-shell` 提供 RAM shell。两者均不提供持久 rootfs。内核启动检查不证明具体主板的网卡、AHCI、显示、 ACPI 表和多核启动可用；设备驱动必须按实际 PCI ID、固件表和中断路由确认。 ACPI 关机通过 uACPI 解析固件的 `_S5` 等睡眠状态并请求断电；具体主板的 AML 与电源结果仍需验收。启动完成须观察 `part ok`，需要时手工断电。
