# Allwinner H616 / H618

`sun50i-h616` 是面向 H616/H618 的 AArch64 板级构建骨架，涉及 Orange Pi Zero 2、Zero 3 和 Zero 2W 的 SoC 地址。它尚未形成可部署系统：DW UART、固件保留内存和 Image 交接未闭合，也没有本板固件或完整 SD 打包工具。不能把三种板型或内存规格当作一个已验证配置。

## 系统支持与具体缺口

| 项目 | 当前 A20OS 状态 |
| --- | --- |
| CPU | 公共 AArch64 内核，board 的 `.smp=NULL`；使用单核 profile，尚未实现本板次核启动。 |
| RAM | 平台头固定 `0x40000000..0x80000000`，即 1 GiB 分配窗口；没有板级 DTB RAM/保留区裁剪。512 MiB 板可能分配到不存在的内存；更大内存板也不会自动利用全部 RAM。 |
| 内核入口 | 公共链接脚本与平台头均使用 `0x40080000`；这不代表 U-Boot 自动装载到了该地址。 |
| UART | UART0 `0x05000000`、IRQ 32，硬件是 DW APB UART。没有本板 `board_console.h`，当前代码落到 PL011 访问，不能称为已实现控制台。 |
| GIC / MMU / 时间 | 声明 GICv2 `0x03021000/0x03022000` 和 24 MHz 通用计时器；公共启动表将低 1 GiB 映射为 Device、`0x40000000..0x80000000` 映射为 Normal RAM，覆盖这些基址，但尚无板级属性/权限验收；board IRQ ops 仍含占位实现。 |
| 固件 / 电源 | board 调用公共 firmware 接口；TF-A 的 PSCI 与 DDR/时钟初始化依赖外部启动链，本板关机/重启未验收。 |
| 存储 / 网络 | MMC、EMAC 只有地址常量，设备枚举为空；没有 sunxi MMC、CCU 时钟复位、EMAC/PHY 驱动，不能挂载 SD 根文件系统或联网。 |
| 用户态 / USB / 显示 | 默认 bring-up 不启动用户态；没有本板 USB、显示、摄像头和输入支持。 |

上游 H616 DTB还为 BL31 描述了 `0x40000000` 起的 256 KiB `no-map` 保留区。仅看到内核入口高于它并不充分：分配器和页表都需要明确处理固件保留内存，不能把固定 RAM 窗口视为已经解析设备树。

## 主机依赖与构建

需要 Linux、GNU make、Python 3.11+、`aarch64-linux-gnu-gcc`/binutils、交叉 libc 开发头，以及项目 Rust 工具链、Cargo 和 `rust-src`。串口观测另需 `tio`。AArch64 Rust soft-float core 由 Makefile 构建。

Debian/Ubuntu 安装示例：

```sh
sudo apt-get install build-essential git curl ca-certificates python3 tio \
  gcc-aarch64-linux-gnu binutils-aarch64-linux-gnu libc6-dev-arm64-cross
```

使用 rustup 配置 Rust 1.96.0；尚无 rustup 时先执行安装器，已有时可跳过前两条命令：

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/a20-rustup-init.sh
sh /tmp/a20-rustup-init.sh -y --profile minimal --default-toolchain 1.96.0
. "$HOME/.cargo/env"
rustup toolchain install 1.96.0 --profile minimal
rustup target add --toolchain 1.96.0 aarch64-unknown-none
rustup component add --toolchain 1.96.0 rust-src
git submodule update --init --recursive
tools/a20 check sun50i-h616
tools/a20 build sun50i-h616 -- -j8
tools/a20 show-vars sun50i-h616
```

等价构建入口：

```sh
make ARCH=aarch64 BOARD=sun50i-h616 ABI=linux BRINGUP=1 \
  DRIVER_DEPLOYMENT=embedded NR_CPUS=1 kernel-only
```

输出位于 `.kernel-build/aarch64-sun50i-h616-*/`；末行 `Kernel-only build complete:` 给出准确 `kernel.bin` 路径。同目录有 `kernel.elf`、对象文件及生成配置。它们不包含 SPL、TF-A、U-Boot、DTB、rootfs 或 SD 分区布局。

```sh
aarch64-linux-gnu-readelf -h -l /替换为构建输出目录/kernel.elf
```

检查实际入口、`PT_LOAD` 和完整内存占用。`make check-arm-board-builds` 是 H616/RK3328 的编译检查入口，不执行硬件启动。

## 部署边界

上游的 Allwinner 启动链可使用 SPL → TF-A BL31 → U-Boot，但必须选择具体板型和 DDR 参数。仓库尚无 `sun50i-h616` 的 prepare 或整卡镜像目标，不能通过本实例从空卡生成可启动系统。

实例虽声明 `kernel-bundle`，当前内核没有 ARM64 Image 头；公共打包器会拒绝缺少 `booti` magic 的产物，不能把 `tools/a20 package sun50i-h616` / `deploy` 当作已完成部署路径。

不要执行旧实例内保留的 raw `mmc read` 偏移和长度：它们没有与实际 SD 布局关联，读取扇区不能代替从 FAT 按文件加载；同样，内核地址不能兼作 DTB 地址。标准 U-Boot ARM64 命令的形式是 `booti <kernel> - <dtb>`，其中 `-` 是无 initrd，DTB 在独立地址，进入内核时指针在 `x0`。当前板级缺口修复前，不提供可启动的加载/写卡命令。

已有工作固件可用于确认板型、RAM 和串口。使用 3.3 V TTL，调试排针位置以具体 Zero 2/Zero 3/Zero 2W 原理图为准，不能共用一个未经核对的针脚编号。实例串口参数为 115200、8N1、无流控。先打开日志，再给板卡上电：

```sh
tio -b 115200 -d 8 -s 1 -p none -f none --script-run never \
  --log --log-file sun50i-h616-firmware.log /dev/ttyUSB0
```

在原有 U-Boot 中可以手工采集：

```text
version
bdinfo
printenv stdout stderr baudrate kernel_addr_r fdt_addr_r
```

`tio` 不发送实例中的自动命令，日志写入 `sun50i-h616-firmware.log`；`Ctrl-T` 后按 `q` 退出。没有 reset 线路配置时人工上电，须在打开串口之后触发启动。旧实例的 `a20 console` 在看到 `System ready` 后会自动发送 `/etc/os-release` 与 `poweroff`，不适合直接观察现有工作系统；使用前必须在实例副本中清空 `target.commands` 和 `target.expect`。

## 验收、故障与后续适配条件

当前可检查实例、编译和 ELF；没有物理启动结论。默认 bring-up 无 shell，实例里的 `/etc/os-release` 或 `poweroff` 不是已实现的用户态交互。未来看到 `System ready (bringup, no userspace)` 也不能推导存储、联网或系统断电成功。

固件完全无输出时先检查供电、调试 UART 和启动介质。固件正常而内核静默时，先处理已知的 UART 类型阻断，再核对 MMIO 映射属性、装载地址、异常级别、DTB 和固件保留区；不能认为主线 U-Boot 支持该板就能直接启动当前内核。

形成可部署平台还需要：具体板型的固定固件构建、正确 DW UART、板级映射验收、实际 RAM/保留区发现、Image/DTB 打包和经核对的 SD 布局，以及定时器/GIC/电源的实机验收。SD 和网络驱动属于额外的系统功能。
