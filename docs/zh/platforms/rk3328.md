# Rockchip RK3328

`rk3328` 是 AArch64 板级构建骨架，包含 RK3328 地址常量和单核 board 配置。它尚不是可部署的 Rock64 或 NanoPi R2S 系统：控制台类型、调试 UART、内核链接地址和启动页表仍存在不一致，也没有可用的板级固件或整卡打包流程。构建成功不能视为硬件启动成功。

## 系统支持与具体缺口

| 项目 | 当前 A20OS 状态 |
| --- | --- |
| CPU | 使用公共 AArch64 内核；板级 `.smp=NULL`，只应构建单核。RK3328 的物理四核不等于已有 SMP 适配。 |
| RAM / MMU | 平台头声明 RAM `0..0x80000000`、入口 `0x80000`，但没有私有链接脚本，实际 ELF 使用公共 `0x40080000` load/entry；启动页表也没有为 RK3328 改成正确的 Normal RAM / Device 窗口。固定 2 GiB 不是固件测量值，不能用于较小内存板的分配。 |
| UART | 平台头选择 UART0 `0xff110000`、IRQ 87；硬件是 32 位访问、寄存器间隔 4 字节的 DW APB UART，当前没有 `board_console.h`，实际沿用 PL011 访问。Rock64 上游调试口还选择 UART2 `0xff130000`、1500000 波特，与本头的 UART0 不同。 |
| GIC / 时间 | 声明 GICv2 地址 `0xff811000/0xff812000` 和 24 MHz 定时器频率；板级 IRQ ops 中 enable/disable/ack/eoi 是占位实现，外设映射和实机中断尚未闭合。 |
| 电源 | board 调用公共 firmware shutdown/reboot；没有本板已验证的 PSCI conduit、电源关闭或重启结果。 |
| 存储 / 网络 | eMMC、GMAC 只有地址声明；设备枚举为空，没有 RK3328 MMC、CRU/GRF 时钟复位或 DWMAC/PHY 驱动。不能挂载 SD/eMMC 根文件系统或联网。 |
| 用户态 / 显示 / USB | 默认 bring-up 不启动用户态；无本板显示、输入及 USB 外设支持。 |

Rock64 与 NanoPi R2S 的调试口、网口和电源线路应分别适配。共享一个 SoC 名称不代表两块板可直接共用固件或 DTB。上游板级资料中的能力也不等于 A20OS 已实现驱动。

## 主机依赖与构建

需要 Linux 主机、GNU make、Python 3.11+、`aarch64-linux-gnu-gcc`/binutils、交叉 libc 开发头，以及项目 Rust 工具链、Cargo 和 `rust-src`。串口观测另需 `tio`。AArch64 的 Rust soft-float core 由 Makefile 构建，不能用安装普通 Rust AArch64 target 代替它。

Debian/Ubuntu 安装示例：

```sh
sudo apt-get install build-essential git curl ca-certificates python3 tio \
  gcc-aarch64-linux-gnu binutils-aarch64-linux-gnu libc6-dev-arm64-cross
```

使用 rustup 配置 Rust 1.96.0；尚无 rustup 时先执行安装器，已有时可跳过前两条命令：

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/a20-rustup-init.sh
sh /tmp/a20-rustup-init.sh -y --profile minimal --default-toolchain 1.96.0
. "$HOME/.cargo/env"
rustup toolchain install 1.96.0 --profile minimal
rustup target add --toolchain 1.96.0 aarch64-unknown-none
rustup component add --toolchain 1.96.0 rust-src
git submodule update --init --recursive
tools/a20 check rk3328
tools/a20 build rk3328 -- -j8
tools/a20 show-vars rk3328
```

等价的单板构建入口：

```sh
make ARCH=aarch64 BOARD=rk3328 ABI=linux BRINGUP=1 \
  DRIVER_DEPLOYMENT=embedded NR_CPUS=1 kernel-only
```

构建输出位于 `.kernel-build/aarch64-rk3328-*/`，末行 `Kernel-only build complete:` 给出本次 `kernel.bin` 的准确位置。同目录包含 `kernel.elf`、对象文件和生成配置；这些不是固件、磁盘镜像或 rootfs。

检查 ELF 时使用构建实际输出的路径：

```sh
aarch64-linux-gnu-readelf -h -l /替换为构建输出目录/kernel.elf
```

当前应特别核对实际 `PT_LOAD` 与入口，而不是把平台头的 `KERNEL_ENTRY` 当作链接器结果。`make check-arm-board-builds` 是 RK3328/H616 的构建检查入口，不运行物理板。

## 部署边界

仓库没有 `rk3328` 固件 prepare 目标、SD 整卡镜像目标或验证过的板级 loader。现有实例声明 `kind="kernel-bundle"`，但内核没有 `booti` 所需的 AArch64 Image 头；公共打包器会以 `kernel lacks the Linux Image magic required by booti` 拒绝它。因此 `tools/a20 package rk3328` 和依赖打包的 `deploy` 不是当前可用部署路径。

实例中保留的旧 handoff 也不能直接执行：把内核地址同时作为 DTB 地址不成立。标准 ARM64 handoff 的 DTB 参数在 `x0`；`booti <kernel> - <dtb>` 中的 `-` 表示没有 initrd，第三个参数必须是独立、有效的设备树。绕过头校验或改用 `go` 不能补齐 UART、RAM 和页表差异。

已有板卡可保留其可工作的 SPL/TF-A/U-Boot，用串口观察和收集固件信息，但不要用当前骨架覆盖工作介质。Rock64 调试串口常用 1500000、8N1、无流控；使用 3.3 V TTL，接线和具体 UART 以该板原理图为准。打开日志后再上电：

```sh
tio -b 1500000 -d 8 -s 1 -p none -f none --script-run never \
  --log --log-file rk3328-firmware.log /dev/ttyUSB0
```

可在已有 U-Boot 中手工执行只读检查：

```text
version
bdinfo
printenv stdout stderr baudrate kernel_addr_r fdt_addr_r
```

`tio` 只转发操作员输入，不重放实例命令；日志写入当前目录的 `rk3328-firmware.log`。`Ctrl-T` 后按 `q` 退出。没有 reset 配置时人工重新上电，已经发生的历史输出不会重放。旧实例的 `a20 console` 在看到 `System ready` 后还会发送 `/etc/os-release` 与 `poweroff` 命令，不适合作为现有工作系统的只读观测器；使用它前必须在实例副本中清空 `target.commands` 和 `target.expect`。

## 验收、故障与后续适配条件

目前可验收的内容是实例解析、编译与 ELF 检查。`System ready (bringup, no userspace)` 只代表 bring-up 初始化阶段，不能证明 shell、存储或网络可用；旧实例中的 `/etc/os-release` 和 `poweroff` 不是本 profile 提供的交互能力。

没有串口输出时应先区分“固件本身没有输出”与“固件正常但 A20OS 无输出”。后者已有明确软件阻断，不能只归因于波特率或 pinmux。物理启动适配至少需要统一链接/装载地址、修正启动映射、实现正确 DW UART 与调试路由、绑定实际 RAM/固件保留区、补 Image/DTB handoff，再验证定时器、GIC 和电源接口。存储和联网需要各自的控制器、时钟复位及 DMA 支持。
