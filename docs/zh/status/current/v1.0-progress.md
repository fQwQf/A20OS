# A20OS 1.0 首波进度台账

> 仍未完成的事项见 [1.0 缺口台账](../gaps/README.md)；本页只描述当前状态。

本文档追踪十二个稳定 V1 工作包的状态视图与交付进展。需求台账由 [1.0 计划](../../releases/v1.0.md) 与 [缺口台账](../gaps/README.md) 统一管理。最新集成状态见 [当前模块状态索引](module-status.md)。

固定的 C0 基线尚未认证。`v0.18` 标签是一个可用的版本标识，不是"完整 C0 负载、平台与性能矩阵已通过"的证据。成对 runner 与协议见[比较协议](../../releases/v1.0-comparison.md)；完整验收的权威仍是 1.0 验收计划。

第一份经机器审计的源码清单是 `v1.0-requirements.json`，由自动化工具生成并校验。它扫描全部项目文本输入，把源码条目候选与人工 triage 的需求分开，并把排除项归类为 third-party、generated、historical、retired-platform、 research-not-committed 或 inventory tooling。前十条需求是优先交付队列；另有一条横切的硬件兼容约束被人工记录。其余活动候选仍是 `needs_triage`。这是首次清单梳理，不是"每个候选都已复核"的声明。扫描器会记录 checklist 与 known-issue 队列条目以及源码短语，不单凭关键词决定范围。候选条目或其源码锚点内容变化时，重新生成并复核。

[缺口台账](../gaps/triage-matrix.md) 列出删除完成项后仍开放的人工复核需求，附来源、工作包对照、当前 C/Rust 归属与下一步验证。它与优先队列重叠。在显式链接到人工需求记录之前，源码条目行在生成的 JSON 里仍是 `needs_triage`；该表不取代剩余的 `needs_triage` 候选。

已提交的 task 生命周期、构造与 exit 切片各自仍是 opt-in 且 C 默认。它们有界的 RV64 SMP2 与保留目标依据索引在[selector 矩阵](module-status.md)与各切片说明中；这些记录只证明各切片的覆盖范围；当前功能状态以编号台账为准，本地候选的生命周期/关键并发结果见 N18/N20 关闭记录。早先一次组合 native-futex 运行观察到 C 工作共享掩码 `00000002`，该历史结果被定位到 first-ready 放置；C/Rust first-ready 放置修复现在让匹配的 RV64 SMP2 运行（32 个 job、总和 4,359,168、工作掩码 `00000003`）通过（每档三次运行）。这关闭的是那次复现，不是调度器性能或更广的放置验收。共享 ext4 extent 事务控制器同样是 opt-in：Rust 拥有有界的 depth-zero extent 规划/trim 排序与回滚决策，C 仍执行块 I/O、分配锁、位图/inode 写入与补偿回调。R3 普通重试用例在成对 C/Rust guest 中通过；注入的补偿失败用例是失败关闭的，留下的镜像会被 `e2fsck` 拒绝。该切片的记录未覆盖跨组、树深或总体性能。

另一次独立的 task-exit SMP 运行在次 CPU 上超时，属无效结果；这是一次失败尝试，不是 1/2 重复样本。独立的 15 次 parent-reap 跟进记录在 task-exit 切片说明中，不得并入该分母。

成对 host 结果索引在 [`docs/zh/net/nat-host-oracle.md`](../../net/nat-host-oracle.md)。其功能用例通过；聚合状态仍是 `EVIDENCE_INSUFFICIENT`，因为 C0 与 Cn 尚未认证。

本页“台账已清空”只说明没有独立的领域功能缺口；N18 关键并发和 N20 本地交付已按[候选记录](v1.0-candidate.md)关闭，N02 当前候选云端 CI 仍开放。历史失败及其后续修复分别记录，不能把历史的“开放”措辞当作新增待办。

其余已验证切片同样有界且 opt-in：保留的 RV32 ILP32D IDL peer/adversary/echod 路径通过了四组严格线格式 guest 与 11 个 Make 测试，它是 RV32 Native ABI 依据，不是整个 ABI=linux 覆盖。UXFS shutdown/mount-state 切片在其封存的 SMP1 内核上通过成对 C/Rust 的正常关机与冷启动检查；open-FD 关机返回 EBUSY，崩溃一致性与更广的后端生命周期仍开放。EEVDF scalar 加 ready-treap 的 Rust 切片通过针对性 host 与匹配的 RV64 SMP2 测试，其性能依据不足。RT/RR 队列与带宽切片也通过针对性 C/Rust RV64 SMP2 功能 guest 与 host 测试；其受控负载测得 Rust +3.95%，不构成性能验收。Native ELF guard 是在 RV64 单核上验证的通用 guard：它在 ABI=linux 下拒绝 Native ELF，而普通 Linux 控制继续；SMP2 的拒绝/shell 挂起用例仍未解决。

x86_64 的 IDL peer、ACK adversary 与 `echod` selector 同样保持 opt-in。四组严格 ABI=both SMP2 QEMU guest 通过：Rust peer 配 Rust 与 C 服务，以及 C 客户端配 Rust 与 C 服务。每组都到达 2/2 CPU、打印 protocol/cleanup 与 shutdown 审计标记、FAT 镜像不变，并以状态 0 自然退出。这不认证性能、ABI=linux Native ELF 行为或 C 默认迁移。
